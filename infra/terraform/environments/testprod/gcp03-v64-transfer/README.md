# G03O to primary V64 transfer

This separate Terraform root describes a single-task Cloud Run Job that copies the retained `g03o-1017` dataset from `espacigo_scratch` to the existing `espacigo` V64 database. Terraform does not manage either SQL instance, database, application service, private-file bucket, secret payload, VPC or state bucket; only the execute-gated Job can append a new contract-key version to the existing secret. Its backend is pinned to bucket `espacigo-testprod-tfstate-447373903153-gcp` and prefix `espacigo/testprod/g03o-1017-v64-transfer/20261020`. Do not initialize that remote backend or read/write its state until the prefix and plan receive review; local validation used `-backend=false`.

`enable_job=false` and `transfer_mode=preflight` are the defaults. The preflight mode performs read-only SQL and object metadata checks. It does not receive Secret Manager access to the source transport key, and its Job has no transport-key environment entry, volume, or mount. Execute mode is a separate gate; it grants the transport-key access needed to authenticate the source artifacts and mounts the exact numeric version only in that mode. It also grants the extra API pause, target object create/delete, and contract-key version-add permissions. It pauses the exact API service and leaves it paused after a successful transfer. A separate reviewed plan in the canonical API Terraform root must set the exact numeric contract-key version returned by the Job and the `g03o-1017` / `g03o-1017/privacy-replay` prefixes before the API is resumed. This keeps the live service configuration in sync with Terraform. If commit state cannot be proven, the API remains paused and copied objects are preserved for inspection.

The Job has two digest-pinned Cloud SQL Auth Proxy sidecars on the existing private subnet. TCP startup probes on ports 5432/5433 gate the importer container, which also waits for both sockets before connecting. Its database identities are the retained source `postgres` login and target `espacigo_migrator_login`; the target connection uses `SET ROLE espacigo_schema_owner` only after the preflight verifies the existing `SET` membership. No roles, ACLs, extension objects or migration rows are created or modified. The source app tables and source V1–V61 ledger are checked before import; primary V1–V64 history and canonical seed data are preserved.

The Job maps the 3,245 referenced evidence objects and one replay registry into `g03o-1017/` in the exact application bucket. It derives source object names from database references and probes only the exact source/destination names; source reads and destination reads do not need bucket-wide `storage.objects.list`. Destination create/delete permissions are granted only in execute mode and conditioned on the dedicated prefix. Create operations use generation-match zero and a unique transfer ID per Job invocation. Rollback deletes only generations returned and verified by this invocation and only after the target database is proven empty; if rewrite status is ambiguous, the object is preserved for preflight reconciliation. The SQL data load, V62 replay-registry derivation, and session/token/notice/outbox sanitation run through one `psql --single-transaction` transaction; V63 columns keep their primary defaults and V64 roles/grants remain untouched.

The API service is defined in `infra/terraform/environments/testprod/gcp`, which owns its Cloud Run service resource; `gcp04-runtime` currently defines the worker and migrator, not the API service. That canonical root now exposes the API contract-key version and both object prefixes as inputs. When services are enabled, it requires a positive numeric contract-key version and checks the exact existing Secret Manager secret resource; the release operator must separately confirm that version is `ENABLED` using metadata only, without reading the payload. After a successful transfer, use the reported key version and the two exact prefixes in the reviewed runtime Terraform release, then resume the API through that reviewed release.

No image has been published and no remote backend initialization, state read/write, active plan, apply, Job execution, Cloud SQL write, Secret Manager write or Cloud Run service update has been performed for this root. A future active plan needs the independently verified exact secret versions, source receipt/manifest/evidence hashes, destination bucket confirmation, pinned image digests, and a separate execution review. Review the expected Cloud Run Job duration, regional compute, artifact transfer and added secret-version costs before enabling execute mode; this PR creates no Cloud SQL instance.
