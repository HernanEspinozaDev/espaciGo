# GCP-03 disposable scratch root

This root is independent of `../gcp` and uses a separate GCS state prefix. It reads the existing VPC/subnetwork and manages only resources named for one scratch `run_id`. It must never be initialized with the persistent root's state prefix. The reviewed database pairing is fixed to N4 `db-custom-N4-2-4096` plus 20 GiB Hyperdisk Balanced; confirm availability before a future apply.

Private backend configuration example, stored under `.local/` with directory mode 0700 and file mode 0600:

```hcl
bucket  = "espacigo-testprod-tfstate-447373903153-gcp"
prefix  = "espacigo/testprod/gcp03-scratch"
```

Use `terraform init -reconfigure -backend-config=<private-file>` for this root only. Set `project_id=espacigo-testprod`, `region=southamerica-west1`, and a unique run ID in private tfvars. Scratch/database and Job gates default to false. Scratch `roles/cloudsql.client` grants use an IAM condition that limits access to the named disposable instance. `enable_job` stays false until the exact pushed digest and temporary secret versions are verified, the credential procedure is reviewed, and the V60 Cloud SQL permission blocker is resolved. Terraform never writes a SQL password or creates a SQL user.

Destroy procedure is deliberately two step and run-specific. The replay Jobs use their own `allow_replay_job_destroy` and `confirm_replay_job_destroy_run_id` gate: first lower only the five Job protections while `allow_scratch_destroy=false`, then disable `enable_job` and review a plan that removes only Jobs and their invoker/actAs bindings. SQL, database, secret metadata and the runtime service accounts remain protected. Role-probe Jobs retain their separate gate.

The scratch teardown gate is independent: first set `allow_scratch_destroy=true` and `confirm_destroy_run_id` to the exact `run_id` while keeping `enable_scratch=true`, review/apply only the protection changes for scratch data and secret metadata, then disable scratch and review/apply the destroy plan. This gate does not lower replay-Job protection. Secret versions are deliberately never Terraform-managed. Never run `terraform destroy` against another root or state prefix.

The separate `enable_role_probe_credential_permissions` gate creates only the temporary credential-operator roles/bindings. Cloud SQL `users.*` permissions are treated as project-scoped: the custom role is narrowly limited to the exact user methods and has a fixed expiry, but can affect SQL users on any Cloud SQL instance in the project during that window. A separate confirmation variable makes this scope/risk explicit. Secret-version permissions attach only to the scratch migrator secret and expire at the same timestamp.

The `enable_role_probe_jobs` gate defines only `role_comment_prepare` and `role_comment_after_reconcile`; it requires the already-existing uploaded image digest and an already-existing active numeric secret version, and creates only Jobs plus per-Job invocation/actAs. It does not grant credential-creation permissions. Each gate stays off by default. See `planning/gcp/gcp03_v60_role_comment_probe_plan_20261016.md` for the current preflight, resource IDs, digest, separated plan sequence, permissions and remaining review decisions. No gate enables itself, and none authorizes SQL, migrations, imports, or Terraform apply without the separate reviewed operation plan.

The independent `enable_observer_job` gate defaults off and adds only the fixed `observe` Cloud Run Job plus its exact operator `roles/run.invoker` binding. It uses a separate `observer_image` digest, the existing migrator service account and its exact numeric secret version, the fixed scratch target, private VPC egress, one task, zero retries, and deletion protection. It requires the already-applied five-job gate to remain enabled so Terraform preserves the current migration Job state; it does not change the five Jobs' image, phase, service account, secret, or IAM. Existing migrator `roles/cloudsql.client`, secret accessor, and `actAs` grants must remain no-op in the reviewed plan. The observer Job is not executed by Terraform.

The independent `enable_owner_history_grant_job` gate also defaults off. It adds one digest-pinned, protected `grant_owner_history` Job and its exact operator invoker binding, using the existing migrator service account and numeric migrator secret. It is separate from the original five Jobs and the observer. The phase verifies all V1–V61 history checksums, bootstrap roles, runtime ACLs, and the exact table owner before issuing one fixed grant: `SELECT` on `public.schema_migrations` to `postgres`, with no grant option. It then checks that the owner can read history while `espacigo_runtime` and PUBLIC still cannot. This grants only audit metadata access to the database owner login; it grants no role membership or global privilege. The following owner `retire` phase rechecks the history before disabling the migrator. The grant is intentionally retained on this scratch database because the owner is not the grantor and cannot reliably revoke it; do not represent it as temporary or promise a revoke. The code is reviewed/merged; its image and a combined Terraform plan have been prepared for review, but the Job has not been applied or executed. Terraform does not execute the Job.

The independent `enable_retired_verification_job` gate defaults off. It adds one protected `verify_retired` Job with its own digest and exact operator invoker binding, using the restricted database-ACL service account and the explicitly numbered owner-secret version. Its fixed observer opens a `READ ONLY` transaction and reports role attributes/membership options, effective TEMP/CREATE, database/schema/history ACLs and grantors, object owners, all 16 runtime permission checks, and the complete V1–V61 checksum result. It collects diagnostics before deciding pass/fail, so a failed retirement remains inspectable. The Job neither alters roles/ACLs nor retires credentials; OCI and Terraform plan require their own review.

Terraform planning is read-only against this root's existing state. A plan-only change does not authorize `apply`, Job execution, SQL, secret versions, database users, restore, or import. An OCI upload, when separately authorized, is a distinct action and must record the exact source commit, archive checksum, repository, tag, and verified remote digest.
