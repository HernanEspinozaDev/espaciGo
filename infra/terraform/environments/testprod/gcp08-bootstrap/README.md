# GCP-08 temporary Cloud Run bootstrap

This separate Terraform root provisions a one-time identity for the initial Cloud Run restore. It does not replace the restricted application deployer used by application release and automatic image rollouts.

## Lifecycle

1. A project IAM operator chooses an RFC3339 `bootstrap_expires_at` no more than 24 hours in the future, runs `python3 scripts/verify_gcp08_bootstrap_expiry.py --expires-at "$GCP08_BOOTSTRAP_EXPIRES_AT"`, then reviews and applies this root with `enable_bootstrap=true`. Terraform rechecks the window immediately before creating any grant, so a stale preview fails closed. The operator uses their own short-lived user credentials with Terraform; no service-account key or manual Cloud console/gcloud IAM edit is part of the procedure. The root uses its own remote state prefix `espacigo/testprod/gcp08-bootstrap`.
2. The one-time grant trusts only the exact `application-rollout.yml` workflow on `main`, from the EspaciGo repository, for `workflow_dispatch` jobs attached to the protected `testprod` environment and initiated by the immutable GitHub account ID `176093371` (`HernanEspinozaDev`, verified via GitHub's public user API). The rollout job also fails closed for other initiating actor IDs before bootstrap authentication. Bootstrap uses direct Workload Identity Federation and does not impersonate the application deployer service account. GitHub documents `actor_id` as the ID of the personal account that initiated the workflow run.
3. The Workload Identity pool and provider display names are each limited to 32 characters by the Google IAM API. Terraform has an apply-time precondition and mocked test assertion for both names so a future edit fails validation before resource creation.
4. The bootstrap preview targets only the three Cloud Run services plus the nine IAM bindings already enforced by `verify_gcp07_plan.py`. Terraform refreshes those targets and their dependencies so stale entries in the canonical state are reconciled against Cloud, while unrelated foundation resources remain out of plan scope. The canonical plan reads only the V67 Cloud SQL instance metadata: a temporary custom role contains only `cloudsql.instances.get`, conditioned to the existing `espacigo-testprod-db` instance and expiring within 24 hours. The database name remains pinned to `espacigo_dms_stage_20261020` by validated protected tfvars and the runtime precondition; Terraform does not issue a database metadata read because Cloud SQL Conditions do not support a Database resource type for narrowing `cloudsql.databases.get`. The V67 secret permissions (`secretmanager.secrets.get`, `getIamPolicy`, and `setIamPolicy`) are granted only on `espacigo-test-database-password-v67`, with resource-name and expiry conditions; they permit metadata and IAM-policy access on that secret, but not reading secret versions or payloads. `setIamPolicy` can change any binding on that one secret during the short window; the Terraform plan validator limits the reviewed plan to the API access binding, while the pinned workflow actor remains trusted with this direct permission. Avoiding that permission would require moving or importing the binding into a different Terraform state owner; the current canonical root owns it, so pre-provisioning it alone would not transfer state ownership. The two IAP policy permissions (`iap.webServices.getIamPolicy` and `setIamPolicy`) expire within 24 hours and are conditioned to the `iap.googleapis.com/WebService` resource type. IAM Conditions does not document a resource-name attribute format for IAP WebServices, so this short-lived grant applies to any IAP WebService policy in the project during the bootstrap window; the Terraform allowlist still limits the planned IAP change to the named private service and approved evaluator. The plan remains private to the runner.
5. The temporary Cloud Run role contains only `run.services.create`, `run.services.get`, `run.services.list`, `run.services.update`, `run.services.getIamPolicy`, `run.services.setIamPolicy`, and `run.operations.get`. `run.services.list` is required by the protected bootstrap plan's collection refresh; the read-only Cloud Run v2 `projects.locations.services.list` probe returned HTTP 403, and the [Cloud Run REST reference](https://docs.cloud.google.com/run/docs/reference/rest/v2/projects.locations.services/list) maps that method to this permission. The role has no delete, Cloud Run Jobs, project IAM, or other service permissions. The IAM policy condition allows only the existing `roles/run.invoker` and `espacigoCloudRunServiceUpdater` grant types. Cloud Run does not expose `resource.name` for IAM Conditions, so this project-level role cannot be conditioned to the three service names. Its exposure is bounded by the exact WIF workflow/ref/environment and a hard maximum lifetime of 24 hours. The separate `iam.serviceAccounts.actAs` role is granted directly on only the API and two web runtime service accounts, with the same expiry. State access is granted only on the existing managed folder `espacigo/testprod/gcp/` using the existing object-only role, and also expires within 24 hours.
6. A separate custom role contains only `iam.roles.get` for the read-only IAM role-definition lookup required by the bootstrap plan. Its project binding targets the same exact WIF workflow principal and uses the same `bootstrap_expires_at` condition; it cannot create, update, or delete roles or policy bindings. During the short window, this project-scoped binding allows reading project IAM custom-role definitions. IAM resources do not provide `resource.name`, and the supported IAM Condition resource-type table does not list IAM Role, so the grant is bounded by the exact workflow principal and expiration rather than an ineffective role-name/type condition ([attribute reference](https://docs.cloud.google.com/iam/docs/conditions-attribute-reference#support_for_inherited_conditions), [resource attributes](https://docs.cloud.google.com/iam/docs/conditions-resource-attributes)). The `roles.get` method requires `iam.roles.get` ([IAM REST reference](https://docs.cloud.google.com/iam/docs/reference/rest/v1/roles/get)).
7. The manual `initial-restore` workflow authenticates directly as that federated principal. Existing preflight checks, migration gate, digest manifest, Terraform plan allowlist, reviewed preview fingerprint, exact apply phrase, and approval environment still apply. The updater service account continues to handle normal release/rollout workflows.
8. Immediately after the reviewed initial restore succeeds, the operator sets `enable_bootstrap=false` and applies this root again. That removes the temporary role grants, custom roles, provider, and pool. IAM conditions independently stop granting access at `bootstrap_expires_at`, even if cleanup is delayed.

The initial enablement and final cleanup require a project IAM operator because the current application deployer is deliberately unable to create IAM roles, modify project IAM, or provision WIF. This root only describes that path; this PR does not run Terraform against Cloud or create any identity or grant.

## Validation

Run `terraform init -backend=false -input=false -lockfile=readonly`, `terraform fmt -check -recursive`, `terraform validate -no-color`, and `terraform test -no-color` in this directory. From the repository root, run `PYTHONPATH=scripts python3 -m unittest scripts.test_gcp08_bootstrap_expiry scripts.test_gcp08_bootstrap_workflow scripts.test_classify_gcp08_terraform_failure`. The tests use a mocked provider and do not need Cloud credentials or the remote backend.
