# Evidencia LOCAL-BOOK-01 — PostgreSQL y conflicto de reserva

Fecha: 2026-10-07. Código probado: commit `aa06d3759312623830d172d1eabd6c07feeb42b8` en la rama del PR de LOCAL-BOOK-01. Base de referencia: `main` `1d79b9af38c4c0d2a85b15e7fbc4c89d56cd2345`.

## Escenarios ejecutados

Comando exacto:

```sh
GO_TEST_RUN=TestLocalBookingTrialPostgresLifecycleAndConcurrentRetry bash scripts/test-m06-local-booking-postgres.sh
```

Resultado: **PASS**. El script levantó PostgreSQL/PostGIS fijado en un contenedor desechable, con `/var/lib/postgresql` sobre tmpfs y red aislada. El test migró una base efímera; creó un rol `espacigo_runtime` y ejecutó el servicio/constraint mediante ese rol. El harness limpió el contenedor, socket y base temporal al terminar.

La integración, además de la cobertura existente dentro de ese caso, verificó:

1. Se prepararon cotizaciones para tres intervalos futuros antes de ocuparlos. El servicio creó dos reservas distintas para el mismo espacio en `[10:00,11:00)` y `[11:00,12:00)`. PostgreSQL confirmó dos reservas `pendiente_de_pago`, dos retenciones activas y dos primeras transiciones de historial.
2. Una inserción runtime que solapaba ambas retenciones falló directamente con `pgconn.PgError.Code == "23P01"`, observando el SQLSTATE de la exclusión GiST activa.
3. Se intentó reservar un intervalo estrictamente solapado usando su cotización vigente mediante el handler HTTP real. La respuesta fue HTTP 409 y el cuerpo no filtró `23P01`.
4. Después del 409, PostgreSQL confirmó cero reservas para la cotización rechazada, cero transiciones asociadas y las dos retenciones adyacentes originales intactas. La operación transaccional no dejó filas parciales.

El test integra el repositorio PostgreSQL, el servicio de booking y `internal/booking/transport/http`; autenticación usa un stub local de sesión para fijar al titular y no introduce acceso de navegador ni a la base de desarrollo.
