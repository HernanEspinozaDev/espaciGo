## Discrepancias y conclusiones

1. **No falta operación OpenAPI/Go para el flujo listado.** En estas fuentes existen categorías/perfiles, CRUD de borrador, zona, horas semanales, bloqueos manuales, galería, publicación y lectura pública. No se encontró una necesidad de esquema nuevo para continuar; no se propone migración de espacios ni se toca KYC.
2. **Recuperación de alta parcialmente confirmada:** este corte cubre el caso en que el cliente recibió el ID y falla una configuración posterior. El contrato de `POST /spaces` no soporta idempotencia/reconciliación si se pierde esa respuesta; se conserva como brecha de contrato, sin encabezado inventado.
3. **Acceso del anfitrión a “ver el anuncio”:** la página pública existe y el editor confirma publicación, pero en `host-listings-list.tsx` y `listing-editor.tsx` no se encontró un CTA/enlace a `/espacios/{id}`. Es una brecha de affordance candidata para el corte de publicación; no se cambia antes del orden del plan.
4. **Evidencia de ramas no equivale a gate de HEAD:** las pruebas nativas de wizard/editor/publicación citadas corresponden a `0659dda`; galería, a `bd4b940`/`f55dec1`. Los componentes UI y/o adaptadores relevantes difieren del candidato `5830c9c`. Se pueden reutilizar como evidencia histórica de su SHA y, donde el backend coincida, de ese contrato backend; no como recorrido nativo de la UI actual.
5. **No repetir mutaciones existentes:** el alta manual online la reportó el usuario; los borradores/fotos/horario/publicación usados por ensayos históricos se conservan. Este inventario no ejecutó POST/PUT, login, base de datos, storage, migraciones ni navegación online.
