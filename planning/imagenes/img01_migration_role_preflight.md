## Identidad migradora y ownership

El SQL propuesto en [reconcile_v64_cleanup_worker_role.sql](../../db/repair/reconcile_v64_cleanup_worker_role.sql) reconstituye solo el rol `espacigo_privacy_cleanup_worker` y los grants de V64 cuando se cumplen sus guards. Verifica base, `session_user=postgres`, checksum y nombre V64, rol ausente y objetos de grant. Si la rutina V64 existe, comprueba owner/seguridad y restaura su permiso EXECUTE; si falta, V73 la crea con `CREATE OR REPLACE`. Acepta únicamente la arista administrativa automática worker → creador `postgres` que PostgreSQL 18 otorga con ADMIN TRUE, SET FALSE e INHERIT FALSE, grantor bootstrap (OID 10); el creador no puede revocarla. Rechaza cualquier otra membresía y toda pertenencia del worker a otro rol. No concede SET/INHERIT a `postgres` ni membresías al runtime. La arista ADMIN permite al owner administrar y conceder membresías del worker; SET/INHERIT FALSE evitan asumirlo accidentalmente y no son una frontera contra ese administrador. Fuente: [atributos de roles PostgreSQL 18](https://www.postgresql.org/docs/18/role-attributes.html). V64 histórica permanece intacta; su ejecución nueva se ensaya por separado en una instalación vacía. No reemplaza la función, no toca el ledger, no reasigna owners ni concede privilegios a otros roles. Es propuesta de DBA; no se ejecutó y requiere revisión/autorización separada.

Para V68, `ALTER TABLE public.espacio ADD COLUMN` requiere ownership o autoridad equivalente; PostgreSQL no ofrece un `GRANT ALTER` de tabla. Además V68 crea FKs hacia `usuario`, `espacio` y galerías. El migrator actual no tiene DDL ni REFERENCES. Por el inventario reportado, ejecutar V68–V74 como el login migrador no es viable. Mantener ese login read-only; una ruta mínima coherente con owners actuales es una ejecución única y revisada del migrador como el propietario existente `postgres` por el forward autorizado, sin conceder `cloudsqlsuperuser` ni más membresías a `espacigo_migrator_login` o runtime. El operador debe revisar hashes/plan/backup y autorizar esa sesión admin antes de aplicar. Si esa ruta no se aprueba, se necesita un rediseño específico de ownership/permiso por objeto; no transferir ownership global.

Nunca elevar `espacigo_runtime`, `espacigo_api_login`, `espacigo_migrator_login` o el cleanup worker para resolver DDL. Mantener `SUPERUSER`, `CREATEROLE`, `CREATEDB`, `BYPASSRLS` fuera de runtime y migrator. El rol cleanup es drift y la reconciliación de arriba no se ha autorizado todavía. Si el preflight encuentra diferencia adicional, registrar operación, objeto y permiso denegado y detenerse; no compensar con grants amplios.

## Orden de migración y release

Cloud Build actual no aplica migraciones. No conectarlo con las credenciales privadas del operador ni reutilizar `_DATABASE_SECRET` de API. El procedimiento disponible depende de la sesión local/túnel y no debe convertirse en un paso de Cloud Build sin identidad de servicio, acceso a secreto y conectividad revisados por separado.

Después de validar que el secreto vigente de `postgres` está disponible al operador autorizado, y con la revisión/autorización que cubra la operación concreta (sin volver a pedir autorizaciones ya concedidas para esa misma operación):

1. Reabrir y revalidar el forward; usar el canal aprobado de secreto a archivo privado, sin valores en argumentos, variables visibles, logs o commits.
2. Ejecutar y revisar el preflight read-only del SHA fijado. Comprobar que el binario exacto implementa `-plan-only` antes de invocarlo: `main` en `937c49c` no lo implementa, el candidato de #533 sí. El comando normal escribe. Validar el SQL exacto de reconciliación, autoridad del owner y autorización DBA; el login read-only no puede aplicar esta reparación. Confirmar backup recuperable satisfactorio y registrar ID/fecha/estado antes de cualquier escritura, incluida la reparación.
3. Tras revisión/autorización, ejecutar la reparación V64 y, como operación separada aprobada, la reparación ACL TEMP anterior. Comprobar rol, atributos, membresías, grants, función y ACL de la base sin consultar datos de negocio. Conservar ledger V1–V67 íntegro.
4. Ejecutar `-plan-only` con `espacigo_migrator_login` para revisar el plan, aunque esa identidad no tiene DDL.
5. Revisar backup, SHA y plan exacto. Para aplicar V68–V74, usar la identidad propietaria `postgres` en una ejecución independiente aprobada; detenerse ante checksum/objeto distinto.
6. Ejecutar postcheck y `-plan-only`; exigir cero pendientes y objetos/privilegios esperados antes de cualquier deploy.

Cloud Build no obtiene acceso a la sesión SSH local. No activar un job ni reutilizar el login read-only como migrator. La ejecución sigue la ruta canónica existente `preflight/plan-only → backup válido → reparación revisada/autorizada → plan V68–V74 revisado → cmd/dbmigrate como owner aprobado → postcheck sin pendientes → release`. No falta diseñar otro transporte: se usa el forward SSH del bastión existente. Una divergencia adicional exige evidencia y propuesta acotada; no omitir guards, reiniciar DMS, requerir SQL Studio ni crear jobs/roles/rutas alternativos. La revisión de código y el ensayo local no acreditan aplicación remota ni autorización SQL por sí solos.
