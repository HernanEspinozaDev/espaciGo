# GCP-03: controles Cloud SQL y procedimiento de compatibilidad

Este corte prepara un plan Terraform independiente para reforzar la instancia existente `espacigo-testprod-pg`. El plan no se aplica. No se ejecutan SQL, migraciones, bootstrap, conexiones de aplicación, creación de usuarios ni versiones secretas, dump, restore o importación.

## Cambios de configuración incluidos en el plan

- `settings.deletion_protection_enabled = true`: protección nativa de Cloud SQL además de `deletion_protection = true` y `deletion_policy = "PREVENT"`, que siguen protegiendo operaciones Terraform.
- `settings.connector_enforcement = "REQUIRED"`: Cloud SQL rechazará conexiones directas que no usen Cloud SQL Auth Proxy o un Cloud SQL Language Connector.
- `settings.ip_configuration.ssl_mode = "ENCRYPTED_ONLY"`: exige TLS para conexiones directas. Los conectores proporcionan TLS y verifican las identidades del cliente y servidor automáticamente.

No se cambia `require_ssl`, `requireSsl` u otros parámetros TLS heredados; se utiliza `ssl_mode`. El plan se conserva fuera del repositorio, bajo `.local/planning/gcp/gcp-03-cloudsql-security-20261016/`, con modo 0600. Hash, resumen de acciones y límites se añaden aquí después de generar y revisar el plan exacto. Su existencia no autoriza `apply`.

Referencias: [recurso Terraform `google_sql_database_instance`](https://registry.terraform.io/providers/hashicorp/google/latest/docs/resources/sql_database_instance), [SSL/TLS de Cloud SQL para PostgreSQL](https://docs.cloud.google.com/sql/docs/postgres/configure-ssl-instance) y [Cloud SQL Language Connectors](https://docs.cloud.google.com/sql/docs/postgres/language-connectors).

## Compatibilidad y preparación de roles: secuencia futura

Cada paso operativo requiere su propio alcance revisado. Antes de conectar cualquier cliente, preservar V1–V61 byte a byte y comparar sus SHA-256 con el checkout aprobado. No modificar `espacigo_pgdata` ni los respaldos fuente; mantener dumps inmutables con hash, tamaño e inventario.

1. **Probar extensiones y esquema en un PostgreSQL 18 descartable.** Registrar `server_version`, `postgis_full_version()` y extensiones presentes en el origen; el origen observado usa PostGIS 3.6.4 y Cloud SQL ofrece 3.6.0. Confirmar en la matriz vigente de Cloud SQL las versiones disponibles para `postgis`, `btree_gist` y `unaccent`. Ejecutar V1–V61, por checksum, sobre una base vacía de ensayo y verificar objetos, índices, funciones, triggers, restricciones y consultas espaciales. La diferencia de PostGIS queda como criterio de salida, no se modifica el origen para ocultarla.
2. **Definir privilegios por función.** Separar el principal migrador del rol `espacigo_runtime`; el migrador debe ejecutar DDL versionado y crear `schema_migrations`, mientras runtime solo recibe los grants de `internal/dbbootstrap.GrantRuntimePermissions` después de la migración. Ensayar todas las sentencias con Cloud SQL PostgreSQL 18: extensiones y roles administrados tienen restricciones distintas a PostgreSQL autogestionado. No asignar `SUPERUSER`, `CREATEROLE` ni permisos amplios por anticipado; si el migrador necesita capacidades elevadas para una extensión, limitar ese permiso a un bootstrap temporal revisado y retirarlo después. Comprobar `rolsuper`, `rolcreatedb`, `rolcreaterole`, membresías, ownership, grants y secuencias con consultas de catálogo antes de promover el scratch.
3. **Crear credenciales solo fuera de Terraform.** Terraform gestiona contenedores de Secret Manager vacíos y sus IAM; una futura operación autorizada generaría los valores en un canal secreto y añadiría versiones fuera del código, plan, logs y state. El principal migrador solo leería `database-migrator-password`; el servicio API solo leería `database-password`. No establecer contraseña ni utilizar el usuario Cloud SQL predeterminado `postgres` para la aplicación. Verificar identidad de cada secreto y acceso IAM antes de cualquier conexión.
4. **Aplicar V60 exactamente una vez como parte de las migraciones V1–V61.** `V000060__gadm_local_bootstrap_restricted_role.sql` crea el grupo `espacigo_gadm_bootstrap` como `NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS NOINHERIT`, rechaza atributos peligrosos o membresías, y concede privilegios específicos por columna/tabla junto con un trigger que impide cambiar el UUID de identidad. Verificar esos atributos, ausencia de membresías y los grants concretos al terminar la migración. Ese grupo no es el migrador, runtime ni una cuenta de servicio; el SQL de V60 no debe reutilizarse como script para habilitar un login de aplicación.
5. **Mantener GADM fuera de este ensayo de Cloud SQL.** `cmd/gadm-admin activate-local` exige `GADM_BOOTSTRAP_ENV=local-activation`, base explícita `espacigo_local`, URL y extremos loopback, archivo de credenciales 0600 bajo `.local/testing/` y frase de confirmación exacta. Es una ruta local deliberada; no acepta la red privada de Cloud SQL. No crear membresía o login temporal en Cloud SQL ni activar un administrador allí sin un cambio de diseño y autorización propios.
6. **Ensayar la ruta privada de conexión antes de datos.** La instancia no tiene IP pública; Cloud SQL Connector no aporta por sí mismo una ruta de red. El cliente debe ejecutarse desde una VPC con ruta privada a la IP `10.189.0.3` sobre Private Service Access y tener `roles/cloudsql.client`. La API ya implementa `cloud.google.com/go/cloudsqlconn` con `WithPrivateIP()`. El binario `cmd/dbmigrate` actual recibe `DATABASE_URL` directo y no inicializa ese conector: para migrar, usar un Cloud SQL Auth Proxy ejecutado en una VM/runner privado aprobado o desarrollar y revisar soporte del conector para el migrador. Nunca desactivar `connector_enforcement` para acomodar una conexión directa. Probar TLS/identidad con un usuario desechable y comprobar el endpoint privado antes de migrar.
7. **Restaurar primero solo al scratch.** Generar un dump consistente `pg_dump -Fc --no-owner --no-acl`, calcular su hash y revisar `pg_restore -l`. Filtrar la lista TOC mediante allowlist revisada para excluir ownership/ACL de extensiones administradas; crear previamente las extensiones compatibles y restaurar en una base descartable. Comparar conteos, secuencias, checksums de migraciones, constraints, índices, objetos PostGIS y consultas de negocio. No importar en `espacigo` persistente antes de que el ensayo pase y exista autorización separada para el target exacto.

La aprobación de este PR revisa código/documentación y el plan guardado, pero no autoriza por sí sola su aplicación.
