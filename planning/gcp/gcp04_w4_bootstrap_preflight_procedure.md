# GCP-04-W4 — procedimiento propuesto de baseline y preflight

**Estado:** propuesta local en revisión; no aprobada para ejecución Cloud. No habilita GCP-04, API, migraciones remotas, worker ni aceptación de producto.

## Propósito y alcance

Definir una operación futura de una sola vez para empaquetar el baseline lógico existente V1–V64, verificarlo antes de transferirlo, y ejecutar un preflight privado y estrictamente de solo lectura sobre la base destino `espacigo` de `espacigo-testprod-pg`. El candidato sigue siendo metadata histórica: instancia PostgreSQL 18 en `southamerica-west1`, IP privada. Cada dato operativo (estado de instancia, red/subred, SQL, versiones secretas, IAM, presupuesto y concurrencia) debe releerse en la ejecución y no se presume vigente.

El trabajo entregado aquí prepara código/SQL y una repetición PostgreSQL local. No usa Google Cloud, no lee/escribe Terraform remoto, no cambia credenciales ni IAM, no ejecuta SQL en el destino, y no crea Jobs. V1–V64 se conservan byte a byte.

## Evidencia y ACL de propietario

`bash scripts/gcp04_prepare_baseline_bundle.sh` ejecuta la repetición W3 con PostgreSQL 18/PostGIS fijado por digest, dos contenedores sin red ni puertos, datos en tmpfs y sockets Unix efímeros. Al finalizar conserva solo el paquete sintético bajo `.local/testing/gcp04-w4-baseline-<run-id>/` (directorio 0700 y archivos 0600); el validador `scripts/gcp04_verify_baseline_bundle.py` vuelve a verificar hashes, TOC, ledger V1–V64, roles, ACL, comentarios y permisos efectivos. El paquete es privado local, no es un artefacto Cloud ni debe copiarse a issues, PR, logs o capturas. Para transferirlo se necesita una decisión posterior sobre ubicación privada, retención, cifrado, IAM de un solo propósito, checksum y eliminación.

La comparación registra diferencias de representación explícita de ACL auto-otorgada por el propietario; no las filtra silenciosamente. En la repetición actual existen ocho entradas explícitas del lado fuente para `public.verificacion_archivo_retiro_pendiente_local`, sin diferencia de privilegios efectivos del owner. El validador requiere todos los privilegios efectivos de tabla/secuencia/rutina/tipo/esquema/base y una correspondencia explícita completa cuando exista ACL. Si la diferencia o los checksums cambian, se detiene la preparación y se requiere revisión del inventario; no se relaja la comparación.

Los hashes completos del dump y del inventario por tabla son propios de cada ejecución efímera: `pg_dump` incorpora un nonce `\restrict` nuevo y los fixtures locales incluyen valores/tiempos de aplicación distintos. No se interpretan como checksum del código o del ledger. La comparación canónica de catálogo y estructura permanece `24d5a0c2f7ffa883ff3fb9fd586d9466763386ac75f1b10c8ed9464175caac5f` y `b79fdc11c32f26ae88ae3a4f05b09fa02821f55d6932f80b23d12560a6ff2511`; el ledger V1–V64 conserva `6878b1fd6f97ec6d955008d2e9a0f9da3c8618c9f8ca8c3899245abbf2295e6e`. Cada ejecución aún exige igualdad source/target de datos dentro de esa ejecución.

Un dump de una base PostgreSQL no contiene los objetos globales de roles; por eso el paquete valida el archivo/TOC y el catálogo por separado y la futura secuencia debe provisionar roles mediante un camino separado. V60 añade comentario al rol GADM y no se debe fingir que restaurar el dump lo crea. La limitación de privilegios de Cloud SQL y el requisito PostgreSQL para `COMMENT ON ROLE` siguen siendo una puerta de compatibilidad abierta; W4 no afirma haberla resuelto. Referencias primarias: [pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html), [COMMENT](https://www.postgresql.org/docs/18/sql-comment.html), [usuarios de Cloud SQL para PostgreSQL](https://docs.cloud.google.com/sql/docs/postgres/users).

## Fases futuras sujetas a liberación explícita

1. **Congelar el candidato.** Volver a leer proyecto, instancia, base, engine, región, estado, red/subred, conexión privada, settings de capacidad y state asociado. Confirmar el destino con la persona responsable. No consultar ni usar el state GCP-03. Un desvío de identidad, estado, topología o versión aborta.
2. **Resolver credencial de lectura.** El SQL necesita una sesión real para inspeccionar el catálogo. No hay versión activa confirmada para los secretos de este corte ni se ha probado una cuenta observer. No inventar, reiniciar ni cambiar password. Seleccionar un login de solo lectura existente o aprobar una creación separada de observer; usar una versión numérica de Secret Manager verificada en el momento de la liberación. Nunca mostrar el valor. Si se requiere un credential administrativo para crear roles, esa autorización/credencial es separada del preflight y no debe reutilizarse como observer.
3. **Resolver bootstrap y V60.** Antes de cualquier restore, revisar un procedimiento de roles separado para Cloud SQL que incluya `espacigo_schema_owner`, grupos runtime y comentarios globales. Debe demostrar mínimo privilegio, no dejar membresías ADMIN OPTION ni un rol GADM asignado, y conservar los comentarios exigidos sin modificar V1–V64. Repetir con PostgreSQL local y validar compatibilidad real mediante una ejecución explícitamente autorizada; de lo contrario, no transferir ni restaurar.
4. **Preparar ubicación y acceso del paquete.** Elegir bucket/ruta privada, cifrado, retención y propietario; crear IAM mínimo temporal con acceso de escritura del empaquetador y lectura del job/verificador únicamente al objeto exacto. Comparar manifest y `SHA256SUMS` antes y después de transferencia. El manifiesto no debe incluir credenciales ni filas de datos. Toda discrepancia aborta; no se “repara” el artefacto en el destino.
5. **Preflight remoto de solo lectura.** Ejecutar `db/query/gcp04_w4_target_preflight.sql` como consulta por Cloud SQL Connector sobre IP privada y VPC existente. Requiere que el login pueda consultar el catálogo y que el cliente proporcione `required_connections` revisado. El informe inventaría objetos en todos los schemas no sistémicos, resalta schemas/objetos no-extension fuera de `public` y lista objetos extension-owned. Las extensiones aprobadas tienen nombres y versiones exactos fijados en la consulta (`btree_gist`, `plpgsql`, `postgis`, `unaccent`); cualquier adición o cambio de versión cierra el gate hasta revisión. El reporte también enumera ACL explícitas, atributos de roles `espacigo_*` y membresías directas y transitivas desde logins de aplicación, con opciones `ADMIN`, `INHERIT` y `SET`. No extrae filas de negocio, contraseñas, hashes, PID, texto SQL ni IP de cliente. Las validaciones del parámetro ocurren antes de la transacción; el reporte de catálogo/capacidad corre en una sola transacción READ ONLY. Si no puede ver un campo, construir JSON, confirmar READ ONLY o completar una sección, falla cerrado.
6. **Puerta de destino.** Para un destino vacío solo se admiten objetos del sistema y objetos pertenecientes a extensiones aprobadas con versión exacta; se requieren cero objetos de aplicación no-extension en cualquier schema, cero schemas de usuario fuera de `public`, ausencia de `schema_migrations`, y roles/membresías/owners/ACL idénticos al contrato firmado. La membresía transitiva efectiva se inspecciona incluso a través de roles intermedios, sin conceder membresías para inspeccionarla. No tratar un esquema parcialmente poblado como vacío. Antes de cualquier carga se requiere una decisión separada que autorice el baseline lógico y un proceso transaccional/recuperable; W4 no incluye ni habilita dicho restore.
7. **Capacidad.** El informe resta del máximo las reservas del servidor, conexiones visibles y filas de actividad no clasificables, produciendo una cota inferior conservadora. Comparar con un presupuesto de conexiones aprobado. `24` se incluye solo como parámetro provisional heredado, no como capacidad aceptada. Si la vista es parcial, no hay datos o el límite es menor al presupuesto, detener y reevaluar.
8. **Estado y aislamiento.** Cualquier futuro root Terraform de preflight debe tener backend/prefix aislado y run-scoped: `espacigo/testprod/gcp04-w4-bootstrap-preflight/<run-id>/default.tfstate`, conservando el bucket existente `espacigo-testprod-tfstate-447373903153`. Este corte no lee, importa ni escribe ese state; tampoco propone aplicar Terraform. Si un root no necesita recursos persistentes, preferir no crear state. La VPC/subred e instancia SQL compartidas no se destruyen ni alteran.
9. **Costo y retiro.** Antes de liberar la ejecución, calcular en el momento el costo de imagen/almacenamiento/transferencia/Cloud Run/Cloud SQL adicional y aprobar límites. La consulta usa recursos efímeros, pero el costo Cloud SQL existente y cualquier transferencia no se estima aquí. Tras ejecutar, revocar el IAM temporal, retirar solo el Job/recurso run-scoped y borrar la copia temporal del paquete según retención aprobada. No borrar instancia, bucket/state, secretos compartidos, red o datos persistentes. Registrar responsable, motivo y evidencia saneada.

## Recurso de ejecución futuro

La opción propuesta es un Cloud Run Job privado de una tarea, con identidad dedicada, Secret Manager montado como archivo desde una versión numérica, Cloud SQL Go Connector con IP privada y acceso por Direct VPC a la red/subred existentes. No tendrá endpoint. La imagen deberá fijarse por digest, ejecutarse como UID no privilegiado, no poner secretos en variables, argumentos ni logs, y emitir únicamente el JSON saneado. La cuenta de servicio requeriría permisos mínimos de conexión a la instancia y lectura del secreto exacto; no se concede en W4. Confirmar límites de concurrencia, timeout, reintentos desactivados o idempotentes y eliminación del job antes de liberar.

## Criterios de salida de esta propuesta

- El paquete local se valida independientemente y sus hashes se incluyen en el registro privado del ensayo; el PR no contiene el paquete ni datos de `.local/testing/`.
- V1–V64 y migrations aplicadas no cambian.
- Se cierra la puerta sobre V60, roles globales, comentarios y ACL con revisión independiente.
- Antes de toda ejecución futura se presentan target identity, versión de secreto numérica (sin valor), IAM, ubicación de artefacto, costo, plan de retiro, capacidad revisada y salida de SQL.
- La autorización de una operación futura no se infiere de la revisión o fusión de este PR.

## Verificación local y límites

La repetición local comprueba replay V1–V64 y baseline lógico contra un clúster PostgreSQL 18 efímero, manifiesto/hash/TOC y las diferencias ACL explícitas/efectivas. Conserva un paquete privado validado. El SQL se ejecuta desde `psql -X -qAt` por socket Unix como el login observer restringido: confirma JSON para destino vacío y poblado, reporta `foreign_app.real_data` (incluida una fila sintética) fuera de `public`, y el observer sigue sin poder leer esa tabla. El harness concede temporalmente `pg_read_all_stats` directo al observer y luego por un grupo intermedio settable, confirma que ambos caminos aparecen en la membresía transitiva y revoca/retira esos cambios dentro del PostgreSQL efímero antes de validar los inventarios finales. También rechaza presupuesto ausente/cero/no numérico y devuelve `passes=false` con capacidad insuficiente. `ON_ERROR_STOP` y el código de salida se validan en cada intento. No valida permisos efectivos del usuario integrado `postgres` en Cloud SQL, conectividad privada, IAM, Secret Manager, Terraform backend ni comportamiento de un Cloud Run Job. No se ha realizado una operación Cloud ni se han usado datos privados de GCP-03/GCP-06.

Ejecución retenida de referencia (19-10-2026, hora local): 98 tablas; manifest body SHA-256 `0a659ca16999d4e60160c407cb175ab4067cac7e1d7923aa8a85813c467f8b34`; archive SHA-256 `5c58e56467545ca80b7c40359a2c8af6c994adc27915d314f27af5b87f33a179`; ledger SHA-256 `6878b1fd6f97ec6d955008d2e9a0f9da3c8618c9f8ca8c3899245abbf2295e6e`. Bundle y salida detallada permanecen excluidos en `.local/testing/`.
