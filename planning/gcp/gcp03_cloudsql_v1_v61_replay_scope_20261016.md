Ver [resultado y límites del probe](gcp03_role_probe_execution_20261016.md) y [ADR propuesto](adr_gcp03_baseline_migrado_v60_20261016.md).

## Secuencia aislada propuesta

1. **Bootstrap**, una ejecución como migrador contra la base vacía exacta. El SQL fijo verifica ausencia de `schema_migrations`, crea extensiones soportadas si faltan y el rol runtime restringido. `espacigo_gadm_bootstrap` ya existe por el probe: el bloque SQL debe validar sus atributos y reutilizarlo, no crear otro rol ni conceder membresías. Capturar `btree_gist`, `postgis`, `unaccent` desde la salida real de `ScratchExtensionVersions` y una lectura de `postgis_full_version()`; registrar la versión efectiva, sin asumir la tabla de compatibilidad como versión instalada.
2. **Reconcile de membresías**, una operación Cloud SQL Admin después de bootstrap y antes de migrar. Preservar solo `cloudsqlsuperuser` en el login migrador, esperar `users.update` y verificar API/roles. Si el resultado es incierto, detenerse y conservar el secreto.
3. **Database ACL**, una ejecución separada como `postgres` usando el secreto owner. Revocar TEMP de `PUBLIC` y CREATE de `PUBLIC` en `public`; conceder TEMP de `espacigo_scratch` y CREATE de schema solo al migrador. Verificar privilegios positivos y negativos del migrador y runtime. No usar la credencial owner en otra fase.
4. **Migrate**, una ejecución como migrador luego de prechecks de roles y ACL. Ejecutar V1–V61 exactamente una vez desde una base vacía, sin alterar archivos/checksums ni importar historial. V60 debe reutilizar el GADM preexistente: exige atributos exactos y cero membresías, aplica grants/trigger/comentario y continúa. Detenerse ante cualquier guardia, error, historial parcial o conflicto; no loops ni replay manual de una fase fallida sin conciliar primero.
5. **Finalize**, como migrador. Verificar las 61 filas/nombres/checksums/runner checksums y timestamps que produjo el runner; aplicar el contrato `GrantRuntimePermissions`; comprobar roles y permisos positivos/negativos de runtime. Auditar ownership de tablas, secuencias, funciones y objetos de extensiones; listar funciones `SECURITY DEFINER`, propietario, `search_path` fijo y EXECUTE grants; verificar restricciones de V60, trigger, grants por columna/tabla y ausencia de privilegios de creación en runtime. Probar consultas e índices espaciales representativos contra las extensiones instaladas.
6. **Retire**, una ejecución como owner `postgres` con su secreto separado. Revalidar historial completo y runtime; deshabilitar login/atributos del migrador y retirar TEMP/CREATE. Después, con operación Cloud SQL Admin separada, revocar `cloudsqlsuperuser`, esperar/confirmar ausencia de otros roles y destruir solo la versión migrador exacta. Rotar la contraseña owner con el CLI y destruir solo su versión exacta cuando la operación se confirme.
7. Tras evidencia completa, preparar planes Terraform separados y exactos para retirar Jobs/IAM temporales. Verificar bindings y custom roles después de su limpieza; los custom roles son soft-delete: guardar IDs/metadata y estado `deleted`/ausencia; no reutilizar esos IDs sin conocer retención/undelete. No eliminar instancia, base ni volúmenes en este cierre.
