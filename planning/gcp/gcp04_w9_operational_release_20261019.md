## CLI y etapas de liberación

`go run ./cmd/gcp04w9release` es metadata-only y dry-run por defecto; los clientes SQL Admin y Secret Manager fijan `X-Goog-User-Project` en `espacigo-testprod` mediante `WithQuotaProject`, sin cambiar ADC ni configuración global. El reporte JSON no incluye passwords ni payloads. La preparación por fases usa dos aprobaciones no intercambiables, ambas con SHA revisado, `decision=approved`, revisor exacto `HernanEspinozaDev`, target, rol y vencimiento máximo de 30 minutos:

- `--prepare-secret-shell` solo acepta `.local/testing/gcp04-w9/shell-release.json` con `stage=secret_shell`. Crea el shell global vacío con replicación `USER_MANAGED` a `southamerica-west1` y etiquetas del release. Verifica el ETag, réplica y cero versiones; el recibo incluye ETag. No genera payload, versión, usuario SQL ni Job. Este shell vacío permite preparar el backend aislado y revisar un plan Terraform real antes de crear una credencial.
- `--execute` solo acepta `.local/testing/gcp04-w9/release.json` con `stage=experiment`. Si el shell fue preparado, exige el mismo release ID, sus etiquetas exactas, inventario vacío y el ETag aprobado en `secret_shell_etag`; un shell distinto o ETag cambiado es colisión. Si el shell sigue ausente, solo permite el flujo directo con aprobación `experiment` y nunca si el documento esperaba el ETag de un shell preparado. Genera 256 bits con `crypto/rand` en memoria, añade una versión global y crea únicamente el login nuevo mediante `users.insert` con tipo y `databaseRoles` explícitos.

Cada fase se registra append-only en `.local/testing/gcp04-w9/journal/`, directorio `0700` y archivo `0600`, con IDs de recurso, ETag, versión numérica, operación y fase; no se guarda contraseña ni payload. Los buffers de bytes que controla el helper se sobrescriben al volver; el SDK crea representaciones transitorias en memoria que el runtime libera según su ciclo normal. Ninguna copia se persiste o imprime. Una respuesta de mutación ambigua o timeout se registra como incertidumbre y no se reintenta a ciegas. Ante rechazo definitivo de `users.insert`, la compensación destruye solo la versión numérica creada en esta liberación usando ETag; Secret Manager conserva esa versión en `ListVersions` como `DESTROYED`. El shell solo se retira si el release ID y purpose coinciden, el inventario contiene únicamente esa versión exacta destruida y el borrado usa el ETag recién leído. Una versión activa, adicional, distinta, un ETag ausente o una lectura incierta impide borrar el shell. La identidad nunca se elimina automáticamente. Si el API no acepta `pg_read_all_settings`, se detiene; no se intenta un rol superior ni alternativo. [Destroy a secret version](https://docs.cloud.google.com/secret-manager/docs/destroy-secret-version), [delete a secret and all versions](https://docs.cloud.google.com/secret-manager/docs/delete-secrets).

La CLI de aprovisionamiento no ejecuta el Job. La creación/configuración del Job y la ejecución del query siguen separadas: el segundo release debe autorizar exactamente una corrida de una tarea, paralelismo 1, reintentos 0, timeout 120 s, bajo el mismo login y digest revisado. La consulta queda fijada por el hash W8 `3fc825934660bbfc965e8d97b2ef7f4648baf2cded6c8871ae6953bd18c70d16`; no acepta SQL arbitrario. No leer `pg_settings`, `pg_stat_activity`, tablas de negocio, `pg_authid`, `pg_shadow`, passwords ni payloads. Limpiar el login y la versión tras la consulta requiere teardown separado, preservando cualquier recurso cuya propiedad no se pueda probar.

El 2026-10-19 `HernanEspinozaDev` aceptó la decisión de diseño de preparar el experimento con el único login nuevo `espacigo_gcp04_w8_catalog_probe` y `databaseRoles=["pg_read_all_settings"]`. Cada etapa Cloud necesita liberación concreta independiente tras revisar sus artefactos. La propuesta del experimento sigue siendo:

- Crear una vez `espacigo_gcp04_w8_catalog_probe` como builtin con `databaseRoles=["pg_read_all_settings"]` explícito en `espacigo-testprod-pg` / `espacigo`.
- Contraseña aleatoria en memoria, guardada solo como versión numérica del secreto global `projects/espacigo-testprod/secrets/espacigo-gcp04-w8-catalog-probe-password`, réplica única `southamerica-west1`; acceso del proceso al secreto sin exportar payload.
- Una ejecución del Job allowlisted W8: 1 vCPU, 512 MiB, 120 s máximo, tarea/paralelismo 1 y cero reintentos; no endpoints ni worker permanente. La salida contiene únicamente catálogo aprobado y queda saneada.
- Ventana máxima de 30 minutos desde la creación de la versión activa/usuario hasta verificación y teardown; custodio técnico ejecutor `HernanMEC`, revisión y custodia de decisión `HernanEspinozaDev`. El shell vacío preparado no contiene credencial ni habilita conexión. Si el alta o query es incierto, no repetir: reconciliar por metadata, ETag, operación y journal privado.
- Teardown inmediato: verificar resultado y eliminar solamente el usuario exacto creado por esta ejecución, destruir su versión exacta y eliminar el shell si fue creado por la ejecución y no conserva versiones. Registrar resultado y verificar ausencia. Si hay dependencia/recurso ajeno o identidad preexistente, detener y solicitar nueva decisión.
- Si `users.insert` rechaza el rol, retirar solo recursos exactos de esta liberación y cerrar sin alternativa de privilegios.

Esta solicitud reconoce que `pg_read_all_settings` permite lectura amplia de variables; el query no lee settings pero el rol sí los podría leer por fuera de él. La guía de `users.insert` define creación de usuarios y su cuerpo `User` expone `databaseRoles`, pero no documenta específicamente la aceptación de este rol predefinido PostgreSQL para este usuario Cloud SQL; eso se comprobaría solo en el experimento, no se presume. [Referencia `users.insert`](https://docs.cloud.google.com/sql/docs/postgres/admin-api/rest/v1/users/insert), [User y `databaseRoles`](https://docs.cloud.google.com/sql/docs/postgres/admin-api/rest/v1/users), [roles PostgreSQL 18](https://www.postgresql.org/docs/18/predefined-roles.html).
