## Proposed route: one-run SQL access, with an explicit privilege boundary

Cloud SQL's Admin API can create a separate built-in PostgreSQL login without knowing or changing the `postgres` password. The documented `users.insert` method requires `cloudsql.users.create`; creating a built-in user without custom `databaseRoles` automatically grants `cloudsqlsuperuser`, including `CREATEROLE`, `CREATEDB`, and `LOGIN`. This is a temporary, elevated bootstrap identity, not the final runtime account. This broad grant is the main risk and is why creation, use, and deletion must be one reviewed, candidate-bound operation. [Cloud SQL user management](https://docs.cloud.google.com/sql/docs/postgres/users), [Cloud SQL `users.insert`](https://docs.cloud.google.com/sql/docs/postgres/admin-api/rest/v1/users/insert), [Cloud SQL permission mapping](https://docs.cloud.google.com/sql/docs/postgres/iam-permissions)

### Phase A — catalog-only observation

1. Build and review the separate immutable SQL inspector image. The binary runs its fixed inspection directly when invoked; it has no `inspect` subcommand or SQL-input path. It opens a `READ ONLY` transaction, rejects any project, instance, database, or run other than the fixed candidate, and contains no DDL/DML path, arbitrary SQL input, or automatic retry. Its allowlist queries only `pg_catalog` metadata, installed extensions, and effective relation privilege booleans. It emits sanitized aggregates, never application rows.
2. Terraform must first create the dedicated Secret Manager **container**, with no versions. The helper requires this exact container to exist with zero versions and immediate destruction TTL; an absent container is a preflight failure. It generates a random one-time password in memory, checks the generated login `gcp06_inspect_<12 lowercase hex>` is absent, adds one credential version to the container, and then calls Cloud SQL Admin API `users.insert` for that exact login on this instance. Do not call `users.update` on `postgres` in Phase A. Because Cloud SQL built-in users receive `cloudsqlsuperuser` when no custom role is specified, this login is CREATEROLE/CREATEDB and elevated. `READ ONLY` constrains the SQL transaction but does not reduce the account's IAM/SQL privileges or make it safe for arbitrary queries. [Cloud SQL user management](https://docs.cloud.google.com/sql/docs/postgres/users)
3. The password must never be in argv, environment variables, source, plans, logs, or chat. Mount only the exact numeric Secret Manager version read-only as mode `0400` into a one-task Cloud Run Job. Its dedicated service account receives `roles/cloudsql.client` under a time-limited IAM Condition constrained to resource type `sqladmin.googleapis.com/Instance` and the exact candidate resource name, plus accessor on this one secret. Use the existing private VPC/subnetwork, one task, parallelism one, zero retries, short timeout, and no public ingress. Google documents this condition for limiting `cloudsql.instances.connect` to one instance. [Cloud SQL IAM Conditions](https://docs.cloud.google.com/sql/docs/postgres/iam-conditions)
4. This account is not presumed to be an application-data observer or table owner. Phase A may report only catalog fields accessible to it and effective `has_*_privilege` booleans. It must attempt no query against `schema_migrations` rows or application tables. If even the catalog allowlist query is denied, record the sanitized SQLSTATE/query identifier and stop. Do not grant itself access, assume ownership, or switch role.
5. After successful observation, the helper reads the exact version only to verify it is bound to the requested login, deletes that exact temporary SQL user with Cloud SQL Admin API, waits for its operation to be `DONE`, verifies the user is absent, destroys the exact Secret Manager version, and verifies state `DESTROYED`. It does not disable the version first. Delete the one-run Job and service account/IAM bindings only in the separately reviewed cleanup plan. Retain sanitized, hash-bound evidence only.

### Phase B — only after reviewing Phase A evidence

The import's actual ownership and catalog state must determine whether V65/V66 can be applied as-is and which role owns each object. Do not assume that `cloudsqlsuperuser` bypasses PostgreSQL ownership rules or can read table rows. Prepare a second exact plan only after Phase A verifies accessible catalog metadata and effective privileges. A migration-ledger row read and V65/V66 DDL remain unverified.

If metadata confirms that `postgres` owns the required imported objects, the viable DDL route is a separately reviewed rotation of its built-in password to a freshly generated value using Cloud SQL Admin API `users.update`, delivered only through a new dedicated Secret Manager version to the pinned one-run Job. This does not require knowing the former value, but it is not reversible to the unknown former password: it is an intentional candidate-only credential rotation whose replacement credential must be retained as the current private admin credential until a later approved rotation. If that rotation is not accepted, stop; do not try to substitute a `cloudsqlsuperuser` user as owner. If the catalog shows another owner, this proposed route does not establish access to it; return to review with that owner and exact missing database grant identified.

The second plan must specify a transaction-safe bootstrap that creates the final NOLOGIN groups and exact one-purpose LOGIN roles, installs V65/V66 under the verified object/migration owner, verifies effective grants and absence of unexpected memberships/ADMIN OPTION, and has a credential/cleanup sequence. The API runtime login, GADM activation login, and test-access login receive only their reviewed group membership. The test-access role retains only V66's column/function grants. Any migration or owner discrepancy stops the operation; do not transfer ownership broadly or change V1–V64.

The Phase B account/bootstrap operation must be a separate approved deployment and run. Do not combine the catalog inspection and DDL in one invocation. It must emit SQL catalog evidence after application and before any Cloud Run API cutover.
