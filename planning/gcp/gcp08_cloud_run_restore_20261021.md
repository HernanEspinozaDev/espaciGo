## Estado y alcance

Este cambio prepara un flujo manual, primero con vista previa, para crear los tres servicios de Cloud Run de `testprod` usando imágenes fijadas por digest publicadas desde `main`. No ejecuta `terraform apply` ni afirma que exista un servicio desplegado. Cuando los tres servicios existan y el control de versión base V67 pase, el flujo automático existente podrá actualizar imágenes.

La restauración inicial permite únicamente la creación de `google_cloud_run_v2_service.api[0]`, `google_cloud_run_v2_service.web["public"]` y `google_cloud_run_v2_service.web["private"]`, además de nueve bindings IAM exactos requeridos para invocación, despliegue, acceso al secreto runtime y entrada IAP al servicio privado para `user:pasteleriahijitos@gmail.com`. El binding IAP privado puede estar ya aplicado y quedar en `no-op`; el resumen conserva esa acción y valida la identidad y el alcance exactos. Rechaza cualquier otro cambio, incluidos recursos SQL, secretos, redes, buckets, cuentas, roles nuevos o cambios de IAM fuera de esa lista. No crea ni modifica contraseñas, logins PostgreSQL o grants SQL.

El destino está fijado a proyecto `espacigo-testprod`, región `southamerica-west1`, instancia Cloud SQL `espacigo-testprod-db`, base `espacigo_dms_stage_20261020`, usuario de conexión `espacigo_api_login`, rol de aplicación `espacigo_runtime` y secreto `espacigo-test-database-password-v67`, versión `1`. El archivo de contraseña nunca entra a Terraform, GitHub Actions ni el artefacto de vista previa.

## Flujo Terraform y controles

1. El workflow `Application rollout` se ejecuta manualmente desde `main` en operación `initial-restore / preview`.
2. El preflight verifica el job de publicación, el artefacto y su manifiesto. Acepta releases `push` normales, o un `workflow_dispatch` solo si el manifiesto dice `publish_only=true`, `contains_migrations=false`, incluye los digests API y web, y repo/SHA/run coinciden con un workflow exitoso de `main`. El trigger automático `workflow_run` no reutiliza publicaciones manuales; estas requieren elegir el release en un preview manual.
3. El job privado inicializa Terraform con el estado remoto canónico y obtiene las imágenes publicadas por release; el plan permanece en el runner y nunca se publica.
4. `verify_gcp07_plan.py` acepta solo los tres servicios exactos y estos nueve bindings: los dos invokers API de los frontends, tres permisos del deployer sobre cada servicio, acceso público al frontend público, invocación del frontend privado por el agente IAP del proyecto, acceso del API al secreto V67 y acceso IAP al frontend privado para la cuenta activa indicada.
5. El resumen descargable contiene solo direcciones permitidas, acciones, imágenes por digest, miembros/roles IAM exactos, SHA, corrida y huella. El validador rechaza bindings omitidos, añadidos o alterados.
6. Una persona revisa el resumen y la huella. `initial-restore / apply` vuelve a calcular el plan, verifica la aprobación y la frase exacta de confirmación y aplica solo el plan privado recién calculado.
7. Tras verificar servicios saludables y el acceso de API a Cloud SQL, los futuros cambios de aplicación en `main` publican imágenes nuevas y el workflow automático hace rollout de cambios de imagen solamente.

Los inputs Terraform llegan por `GCP07D_TFVARS_JSON`; el workflow fuerza el target V67, fija la versión del secreto, conserva la fundación, Mailpit y Private Services Access existentes, apaga la creación de Cloud SQL, el edge y los Jobs GCP-06, y fija el único principal permitido para el servicio privado. `iap_evaluator_members` sigue controlando solo Mailpit; `private_web_iap_evaluator_members` controla solo Cloud Run. La lectura del state remoto confirma ambos bindings actuales con `user:pasteleriahijitos@gmail.com`, igual a la cuenta GCP activa. El cambio separa los inputs y mantiene la lista actual de Mailpit intacta. `enable_private_services_access=true` mantiene el rango reservado y el peering `servicenetworking-googleapis-com` aunque `enable_database=false`; el plan solo puede aceptarlos como `no-op`.
