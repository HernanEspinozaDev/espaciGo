# GCP-04-W7 — runner privado de preflight SQL

**Estado:** implementación local y plan de infraestructura OFF revisables; ejecución contra Cloud SQL bloqueada hasta acreditar un login PostgreSQL dedicado de mínimo privilegio. No es aceptación de GCP-04 ni autorización de despliegue.

## Alcance implementado

`cmd/gcp04preflight` ejecuta únicamente `db/query/gcp04_w4_target_preflight.sql`, con transacción PostgreSQL `READ ONLY`, presupuesto de conexiones explícito y salida JSON saneada. Verifica en código el SHA-256 del archivo fuente (`6bfb8f0ac959bcda27de6a7e5442606d1be559e5dacf992a6e1e8af91a1f838b`), extrae el cuerpo SQL del wrapper de `psql`, reemplaza sus tres parámetros psql por un parámetro `$1` de `pgx` y rechaza cambios de hash o de forma. La identidad del proyecto, connection name, IP privada, base y login está fijada en el binario. El login candidato es `espacigo_gcp04_w7_observer`; su existencia y grants en Cloud SQL no están comprobados. La consulta requiere `GCP04_PREFLIGHT_SECRET_VERSION` numérico, archivo montado y protegido, deadline de máximo 15 minutos y concurrencia exactamente 1. La configuración Terraform limita el tiempo a 900 segundos, fija por defecto 120, y usa un solo task/paralelismo 1/retries 0.

El proceso devuelve `passed` con código 0, `gate_failed` con código 2 cuando el presupuesto conservador o el contrato observer no pasan y `failed` con código 1 ante error. Antes de iniciar la transacción o consulta, compara el `RemoteAddr` TCP del socket del Cloud SQL Connector con `10.189.0.3`; tanto en éxito como en discrepancia registra IP esperada y observada en JSON saneado. Errores operativos se sanitizan; nunca se imprime la contraseña ni detalles de conexión. El digest de imagen remoto queda sujeto al Artifact Registry aprobado; el scaffold exige la ruta W7 y digest inmutable.

La validación exige el esquema completo de base, motor PostgreSQL 18, capacidad, destino/inventarios, roles, membresías, extensiones, historial, ACL y privilegios efectivos. Comprueba la coherencia de los conteos de inventario y de capacidad (`max - reserves - backends visibles - filas no clasificadas`, con piso 0), y que el `passes` reportado corresponda al presupuesto solicitado. Exige `LOGIN INHERIT` sin `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `REPLICATION` ni `BYPASSRLS`, y exactamente la membresía heredada permitida al grupo `espacigo_db_observer`, sin admin/set. La allowlist ACL para ese grupo solo permite `CONNECT` en `espacigo`, `USAGE` en `public` y, si existe el ledger, `SELECT` en `public.schema_migrations`; rechaza grants de escritura, grant options, ACL por defecto y ACL directas al login. Duplicados del mismo privilegio permitido se aceptan porque pueden corresponder a grantors distintos sin ampliar el privilegio efectivo. La propiedad de base, schema y cualquier objeto inventariado tampoco puede pertenecer al login ni al grupo. Una respuesta incompleta falla cerrada; privilegios o membresías extra producen `gate_failed`. Terraform también compara la IP privada de metadata del recurso Cloud SQL con la IP aprobada y se niega a planificar el Job si no coincide.

`destination_candidate_observed` es solo una observación derivada de los catálogos. La salida fija `restore_approval: not_granted`; ni `passed` ni la capacidad son aprobación de restore, liberación global ni aceptación del producto.

## Metadata observada y límite de identidad

La lectura de metadata de Cloud SQL confirmó proyecto `espacigo-testprod`, instancia `espacigo-testprod-pg`, región `southamerica-west1`, PostgreSQL 18, estado `RUNNABLE`, conexión `espacigo-testprod:southamerica-west1:espacigo-testprod-pg`, IP privada `10.189.0.3` y bases `postgres` y `espacigo`. La lista de usuarios devolvió solo `postgres`. No se observó catálogo SQL, roles/grants, contraseña, ni lectura de payloads de secretos. No hubo conexión SQL remota.

La documentación oficial establece que un usuario builtin creado por Cloud SQL sin `databaseRoles` personalizados recibe `cloudsqlsuperuser`; esa cuenta no sirve como observer. Cloud SQL Admin API permite `users.insert` con `databaseRoles[]`, pero la documentación requiere que el rol de base exista previamente. La existencia de `espacigo_db_observer` solo aparece en fixture local, no en metadata. Por eso no se crea el login ni se configura contraseña. No resetear `postgres`, no usar SUPERUSER/impersonación, no crear roles por SQL remoto y no leer secretos. La creación segura requiere verificar primero el grupo de solo lectura con una identidad ya autorizada; entonces revisar una operación Admin API explícita para crear únicamente el login con `databaseRoles=["espacigo_db_observer"]`, sin omitir roles y sin asignar `cloudsqlsuperuser`. Si el grupo no existe, detenerse para una decisión y secuencia separada revisada.

Referencias: [usuarios Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/users), [crear/administrar usuarios y roles](https://docs.cloud.google.com/sql/docs/postgres/create-manage-users), [recurso Admin API users](https://docs.cloud.google.com/sql/docs/postgres/admin-api/rest/v1/users).
