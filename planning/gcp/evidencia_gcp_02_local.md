- Rama local: `codex/infra/feature/gcp-02-terraform-testprod`.
- Alcance: Terraform, inventario, documentación de topología y estimación local. Se usó la identidad gcloud existente solo para lecturas seguras del proyecto; no se autenticó con Cloudflare. No se ejecutó `apply`, `import`, lectura remota de state, mutación IAM/DNS, ni creación/cambio de recursos.
- Providers fijados en `.terraform.lock.hcl`: `hashicorp/google` 8.7.0, `hashicorp/google-beta` 8.7.0 y `cloudflare/cloudflare` 5.24.0. Los gates de apply tienen defaults falsos; los toggles activos solo se usaron con mock providers en Terraform test.
- Topología IAP propuesta para implementar en una fase posterior: IAP directamente en el servicio Cloud Run privado, con audiencia nativa Cloud Run; el backend del balanceador no declara IAP. La configuración queda tras gates apagados.
- Egreso IAP del SSR privado: `frontend/src/iap-assertion.mjs` descarga actualmente `https://www.gstatic.com/iap/verify/public_key`. La documentación oficial incluye `gstatic.com` y `*.gstatic.com` entre los dominios admitidos por Private Google Access; Cloud Run documenta el uso de PGA en la subred para requests internos por VPC. La VPC conserva su ruta `0.0.0.0/0` por el default internet gateway, necesaria para la ruta estándar PGA; el acceso a los servicios Google permanece dentro de la red de Google. Esto no equivale a salida genérica a Internet ni requiere Cloud NAT para esta llamada concreta. No acredita la conectividad real del proyecto: `confirm_pga_iap_key_preflight` exige una prueba real antes de habilitar Cloud Run; si falla, el servicio permanece apagado y se evalúa/cotiza otra ruta. Fuentes: https://docs.cloud.google.com/vpc/docs/private-access-options, https://docs.cloud.google.com/vpc/docs/configure-private-google-access y https://docs.cloud.google.com/run/docs/securing/private-networking.
- Dependencias de primer apply: la raíz GCP gestiona 13 APIs (incluye Cloud Resource Manager para IAM de proyecto y Service Usage). Los recursos que necesitan servicios esperan `google_project_service.required`; Cloud Run API espera Storage object IAM, los IAM grants de los secretos y Cloud SQL Client; SSR espera `api_invoker`; la service identity IAP se genera antes de su binding; el forwarding rule espera invoker público/IAP. Se generó `terraform graph` en una copia temporal sin backend y se verificaron los arcos API→identidades/recursos, grants→API/SSR y bindings→forwarding rule. Terraform test con mocks valida que el grafo no contiene ciclo y los gates se evalúan, pero no simula tiempos de propagación en Google APIs.
- State previsto en buckets independientes de bootstrap, GCP y Cloudflare. El bootstrap inicial sigue usando state local restringido; la migración al bucket `bootstrap` es un paso manual explícito que aún no se ha realizado.
- Plan local: `terraform fmt -check -recursive infra/terraform`; `terraform validate` en las tres raíces. Las pruebas Terraform mock cubren gates habilitados y negativos: GCP foundation, SQL, Cloud Run/edge, rechazo de foundation sin inventario/política/costo, rechazo de servicios sin preflight PGA/IAP-key, sin versiones de secretos o sin bootstrap SQL, y Cloudflare DNS-only/rechazo sin revisar zona (GCP 7 runs y Cloudflare 2 runs pasaron).
