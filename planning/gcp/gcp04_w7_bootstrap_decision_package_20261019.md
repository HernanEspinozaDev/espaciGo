# GCP-04-W7 — paquete de decisión para bootstrap del observer

**Estado:** propuesta local de decisión, no autorización operativa. No se abrió sesión SQL remota ni se llamó a Cloud SQL Admin API para crear, actualizar o borrar usuarios. No se leyó ni creó ningún secreto, no se cambió IAM/ACL y no se publicó ni ejecutó infraestructura.

## Decisión que falta

Elegir una sola ruta, sin sustitución automática:

1. **Actor SQL preexistente, nombrado por su responsable.** Identificar el nombre exacto del login y acreditar en una sesión directa de solo lectura sus atributos y concesiones. Es la ruta preferida si existe un actor que satisface el contrato de la tabla siguiente. La evidencia de control plane actual no identifica ninguno. El usuario `postgres` aparece en `users.list`, pero queda excluido por las instrucciones vigentes y no se propone usarlo.
2. **Autorizar o rechazar una cuenta temporal de bootstrap builtin con `cloudsqlsuperuser`.** El alta builtin sin roles DB asignados recibe ese rol y, de acuerdo con Google, los atributos `CREATEROLE`, `CREATEDB` y `LOGIN`, además de privilegios limitados de superusuario propios del servicio administrado. `cloudsqlsuperuser` no es el atributo PostgreSQL `SUPERUSER`: Cloud SQL no permite clientes con ese atributo. Aun así, es una elevación explícitamente excluida por la política actual y aquí solo se presenta para decisión; no se crea ni se usa. Asignar un rol custom al alta no es una salida de mínimo privilegio para bootstrap: Cloud SQL exige que el rol custom ya exista, que es justamente lo que falta crear.

**Respuesta requerida para desbloquear el diseño:** indicar el nombre del actor existente para ruta 1, o decidir explícitamente ruta 2 (aprobar/rechazar la elevación descrita), o detener W7. Aprobar ruta 2 no autorizaría por sí mismo la ejecución; seguirían haciendo falta revisión y liberación operativa separadas, resolver `PUBLIC TEMP`, la membresía API y la política de retiro del grupo. No se infiere silencio como aprobación.

## Actor preexistente: capacidades exactas a verificar

La verificación debe ejecutarse con conexión SQL directa autenticada como el login nombrado y sin `SET ROLE`. Registrar `session_user` y `current_user`; exigir que sean el mismo login. Consultar catálogos en modo de solo lectura y fallar cerrado si falta alguna fila/inventario o hay privilegios desconocidos.

| Ámbito | Mínimo requerido | Comprobación y límite |
| --- | --- | --- |
| Atributos del login | `LOGIN`, `CREATEROLE`; `NOSUPERUSER`, `NOCREATEDB`, `NOREPLICATION`, `NOBYPASSRLS`; membresía efectiva y directa admisible | Consultar `pg_roles`, `pg_auth_members` y `pg_has_role`; sin asumir atributos a partir de IAM o `users.list`. |
| Base `espacigo` | `CONNECT` con `GRANT OPTION`, o ser propietario | `CREATEROLE` no implica propiedad ni grant option. No alterar propietario. |
| Schema `public` | `USAGE` con `GRANT OPTION`, o ser propietario del schema | No necesita ni debe recibir `CREATE`. Capturar el grantor exacto de cada ACL para una compensación limitada. |
| Ledger `public.schema_migrations` si existe | `SELECT` con `GRANT OPTION`, o propiedad del objeto | Ningún permiso a tablas de negocio, grants por defecto, ACL amplias o acceso a datos de aplicación. |
| Sesión/transporte | Login directo aprobado, endpoint privado esperado y consulta solo de catálogos | No leer, solicitar, restablecer ni registrar contraseñas/tokens. La cuenta `postgres` no es una opción. |

El actor de desarrollo no debe ser el login observer. Crear el grupo con un actor no superusuario `CREATEROLE` puede conferirle ADMIN OPTION sobre el rol nuevo que PostgreSQL no permite quitar por el propio creador. El patrón candidato separa el actor nominativo de un executor efímero `NOLOGIN CREATEROLE`, usado solo para crear el grupo y separado de los ACL del ledger. No entregar `ADMIN` sobre el grupo al login observer.

## Estado probado y límites de conocimiento

La lectura previa de metadatos del proyecto `espacigo-testprod` encontró la instancia `espacigo-testprod-pg` (PostgreSQL 18, región `southamerica-west1`) y `users.list` devolvió `postgres`. La prueba IAM `projects.testIamPermissions` evidenció permisos de control plane, incluido crear/borrar usuarios, pero no demuestra `CREATEROLE`, grant options ni ownership PostgreSQL. `users.list` tampoco es un inventario de catálogos SQL. La identidad que ejecutó aquella lectura no se publica en este paquete. La evidencia privada saneada sigue bajo `.local/testing/`.

Google distingue el atributo PostgreSQL `SUPERUSER` —que clientes Cloud SQL no pueden tener— del rol administrado `cloudsqlsuperuser`, que sí confiere privilegios elevados y no es un rol ordinario de mínimo privilegio. No son equivalentes; tampoco se debe rebajar `cloudsqlsuperuser` a “no privilegiado”. La documentación oficial dice que un alta builtin sin roles DB asignados obtiene `cloudsqlsuperuser` y `CREATEROLE`, `CREATEDB`, `LOGIN`; con roles custom, estos deben existir antes y se evita el grant automático. La documentación de `users.insert` no garantiza los flags de membresía PostgreSQL `ADMIN`, `INHERIT` y `SET` para `databaseRoles`. Solo catálogo remoto aprobado podría probarlos.

## Efectos durables y cambio mínimo no aplicado

1. **`PUBLIC TEMP=true`:** la corrección candidata exacta sería `REVOKE TEMPORARY ON DATABASE espacigo FROM PUBLIC`, si la ACL actual confirma que ese es el grant que produce el privilegio efectivo. Cambia el comportamiento durable de todos los usuarios que dependan de tablas temporales; antes requiere buscar y probar consumidores, acordar ventana, capturar ACL/grantor y preparar compensación exacta. No se aplicó ni se declara inocua. Si el `TEMP` procede de otra concesión, esta sentencia no resuelve por sí sola el baseline.
2. **Actor sin `CREATEROLE` o grant options:** cambio mínimo no demostrado. No cambiar propietarios ni otorgar privilegios amplios. La resolución preferida es nombrar/verificar un actor preexistente admisible; de no existir, la opción de elevación builtin requiere decisión expresa y revisión independiente. No elevar una cuenta normal en silencio.
3. **`users.insert` no deja los flags requeridos:** no ejecutar un `GRANT` adicional de membresía hasta saber quién es grantor y quién puede corregirlo. Corregir `SET`/`ADMIN` podría requerir una operación de catálogo de privilegio equivalente y dejar una membresía o grantor durable. La API documentada no garantiza tales flags. Parar y solicitar diseño/revisión del steward; nunca `cloudsqlsuperuser` como reparación automática.
4. **Retiro de objetos:** retirar un login creado para este run y su secreto/versiones exactas es reversible solo parcialmente (operación y auditoría permanecen). El grupo observer y ACL `CONNECT/USAGE/SELECT` son durables si se adopta reutilización inerte (`NOLOGIN`, sin miembros); borrarlos requiere capacidad `ADMIN` y revocación exacta por grantor. La política de stewardship —conservar rol inerte o aprobar steward de `ADMIN` para retiro físico— debe resolverse antes de ejecutar.
