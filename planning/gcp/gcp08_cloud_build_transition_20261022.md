# GCP-08: transición a Cloud Build

## Decisión

El despliegue de aplicación se prepara como `main` → Cloud Build → Artifact Registry en `southamerica-west1` → Cloud Run. GitHub Actions conserva sus controles de calidad y validaciones de PR; deja de publicar imágenes o ejecutar Terraform para Cloud Run. Cloud Build será el único propietario automatizado de revisiones, configuración y tráfico de los tres servicios, además de los enlaces de invocación requeridos por las cuentas runtime y el agente IAP. El revisor administra en Console la política de personas/grupos autorizados por IAP.

Terraform conserva la red compartida, Cloud SQL privado como servicio externo, registro, bucket de archivos, secretos y cuentas runtime. El PostgreSQL 18 `espacigo-testprod-db` y la base `espacigo_dms_stage_20261020` se operan mediante el procedimiento manual existente. No se administran con Terraform, no se importan, no se recrean y no se cambian sus roles, grants, esquema o filas. Los recursos Cloud Run ya registrados en state se olvidan mediante bloques `removed` con `destroy = false`; no se ejecuta ese cambio en este PR.

La ruta de publicación queda configurada en `cloudbuild.yaml`. Terraform prepara la cuenta `espacigo-cloud-build-deployer`, sus roles mínimos y un bucket dedicado, y añade Cloud Build y Container Analysis al set de APIs de foundation. Ninguno de esos cambios se ha aplicado. La conexión GitHub y trigger siguen como pasos de Console. Cloud Build habilita IAP nativo en el servicio privado y da `roles/run.invoker` al agente IAP; el revisor conserva el control exclusivo de la política IAP de usuarios/grupos en Console.

## Parámetros y límites

- Proyecto `espacigo-testprod`, región `southamerica-west1`, repositorio Artifact Registry `espacigo-testprod`.
- API: `espacigo-test-api`, puerto 8080, 1 CPU siempre asignada, 1 GiB, mínimo/máximo 1, concurrencia 80, VPC `espacigo-testprod`, subred `espacigo-testprod-api-serverless`, egress `PRIVATE_RANGES_ONLY`.
- SSR público y privado: servicios `espacigo-test-public` / `espacigo-test-private`, puerto 4000, 1 CPU y 1 GiB, mínimo 0 y máximo 1, concurrencia 40, ingreso `internal-and-cloud-load-balancing`, VPC `espacigo-testprod`, subred `espacigo-testprod-serverless` (inventariada como `10.80.0.0/24`), egress `PRIVATE_RANGES_ONLY`. Así, SQL/Mailpit y otros destinos privados usan Direct VPC; las llamadas SSR a la URL pública de Cloud Run API e IAP salen por la ruta internet de Cloud Run y no requieren Cloud NAT.
- Timeout configurado: 300 segundos. API privada por IAM; web pública con invocación pública y controles de aplicación; web privada con IAP. El balanceador HTTPS, NEG, Cloud Armor, certificados y DNS conservan la arquitectura de Santiago.
- PostgreSQL runtime: instancia `espacigo-testprod-db` RUNNABLE/PostgreSQL 18, conexión `espacigo-testprod:southamerica-west1:espacigo-testprod-db`, base `espacigo_dms_stage_20261020`, secreto de contraseña `espacigo-test-database-password-v67` versión 1. Metadatos revisados confirman versión ENABLED `1` para cada secreto de contrato y webhook de pago. No ejecutar migraciones durante build o despliegue ni leer payloads.
- API usa la subred inventariada `espacigo-testprod-api-serverless` (`10.81.0.0/26`); SSR usa `espacigo-testprod-serverless` (`10.80.0.0/24`). Mailpit está RUNNING en la subred privada `espacigo-testprod-mailpit`, IP `10.81.1.2`, SMTP 1025. El proyecto no tiene Cloud NAT/router visible; por eso SSR usa `PRIVATE_RANGES_ONLY`: SQL/Mailpit usan Direct VPC y llamadas a la URL pública de la API conservan la salida pública de Cloud Run sin NAT.
- El bucket de archivos real es `espacigo-test-files-447373903153-gcp02`; no se reutiliza para source staging ni locks. Terraform crea el bucket único `espacigo-testprod-cloud-build-447373903153` con UBLA, Public Access Prevention, `force_destroy=false`, `prevent_destroy` y borrado de objetos bajo `source/` luego de 30 días. No se reutiliza el bucket de archivos ni el bucket/managed folder del state Terraform.
- Los hosts, versiones de secretos y dirección SMTP se verificaron como metadatos/atributos, sin leer payloads. Se fijan directamente en `cloudbuild.yaml`; no quedan variables de reemplazo ni una identidad IAP personal escrita allí.
- El build orquestador ejecuta un build de imágenes hijo una sola vez por commit. `cloudbuild-images.yaml` usa el campo `images` de Cloud Build y `requestedVerifyOption: VERIFIED`, por lo que exige provenance antes de marcar exitosa la publicación. El orquestador valida su presencia y despliega por digest. No usa `docker push` explícito. Habilitar Cloud Build, Artifact Registry y Container Analysis APIs solo durante la activación aprobada.

Cloud Build serializa despliegues con un objeto de lock creado condicionalmente en el bucket dedicado `espacigo-testprod-cloud-build-447373903153`. El mismo bucket aloja el source staging y el lock; el rol de bucket está limitado a este bucket. Si cualquier paso falla, el lock permanece para impedir que una ejecución posterior se adelante; el operador revisa el build fallido y solo retira el objeto tras comprobar que no hay un despliegue activo. Un watermark compara el tiempo de creación del build con el último despliegue exitoso y rechaza ejecuciones antiguas.

## IAM a provisionar en activación separada

Terraform prepara la cuenta `espacigo-cloud-build-deployer`, distinta de las identidades runtime, y los grants acotados descritos aquí. El trigger debe seleccionarla explícitamente; el campo `serviceAccount` de YAML no determina la identidad de builds invocados por trigger. El revisor comprueba que el plan exacto contenga solo estos grants y que el operador que crea el trigger tenga `iam.serviceAccounts.actAs` sobre esa cuenta. Conceder solamente:

- `roles/artifactregistry.writer` sobre el repositorio de imágenes existente.
- El rol custom `espacigoCloudBuildDeployer`: `run.services.create`, `run.services.get`, `run.services.list`, `run.services.update`, `run.services.getIamPolicy`, `run.services.setIamPolicy`, `run.operations.get`, `run.revisions.get`, `run.revisions.list`, `cloudbuild.builds.create`, `cloudbuild.builds.get` y `serviceusage.services.use`. No concede `run.services.delete`, `run.jobs.*`, Secret Manager ni SQL.
- `roles/iam.serviceAccountUser` sobre sí misma para el build hijo y sobre las cuentas runtime API, web pública y web privada.
- Escritura de logs (`roles/logging.logWriter`), `roles/artifactregistry.writer` limitado al repositorio `espacigo-testprod`, y el rol custom `espacigoCloudBuildBucketOperator` sobre el único bucket de Cloud Build. Este rol contiene `storage.buckets.get` y solo los permisos de objeto `create`, `delete`, `get` y `list`.
- `run.services.setIamPolicy` para que Cloud Run conserve el enlace `roles/run.invoker` del agente IAP. No conceder `iap.webServices.*`: la política de usuarios IAP se edita manualmente por el revisor en Cloud Run Console. No conceder permisos para administrar IAP de balanceadores, túneles o servicios ajenos.
- `cloudbuild.builds.get` para que el paso de orden compare el `createTime` del build invocador.

Las identidades runtime conservan sus permisos actuales de Cloud SQL, Secret Manager y Storage. La cuenta de build no recibe permisos de lectura de secretos de aplicación ni de acceso SQL. Terraform también prepara Cloud Build y Container Analysis API bajo `enable_foundation`; el plan exacto debe revisar esos enables junto con el bucket y la cuenta. Cloud Build administra revisiones/configuración Cloud Run y los enlaces `run.invoker`; `HernanEspinozaDev` es el único operador Cloud de activación y dueño humano de los permisos IAP de usuarios en Console.

Google documenta `roles/run.admin`, `roles/iap.admin`, Artifact Registry Reader y Service Account User como roles suficientes de referencia para configurar IAP en Cloud Run; aquí se usan roles custom más pequeños, limitados a los permisos y recursos anteriores. Las políticas de acceso de usuarios IAP se conservan y se versionan bajo ese único dueño durante la activación. [Permisos Cloud Run](https://docs.cloud.google.com/run/docs/reference/iam/permissions), [configurar IAP en Cloud Run](https://docs.cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run), [gestionar acceso IAP](https://docs.cloud.google.com/iap/docs/managing-access), [cuenta de servicio de Cloud Build](https://docs.cloud.google.com/build/docs/securing-builds/configure-user-specified-service-accounts).

## Secuencia manual de activación

1. Revisar este PR y el plan canónico; confirmar que el inventario real de Cloud Run, IAM, IAP, hosts y políticas coincide con los nombres y valores documentados.
2. Revisar el plan Terraform exacto del cambio de state y preparación de Cloud Build: solo debe olvidar bindings Cloud Run/IAP conocidos con `destroy=false`, crear el bucket/identidad/roles nuevos y habilitar Cloud Build y Container Analysis; nada más. Confirmar cero cambios de SQL, datos, red, edge, DNS, balanceador o tráfico. Detenerse si propone destruir Cloud Run, alterar Cloud SQL/grants/filas, leer secretos o reemplazar recursos preexistentes.
3. `cloudbuild.yaml` ya contiene las versiones ENABLED verificadas `1` de contrato, webhook y contraseña SQL, y el IPv4 privado Mailpit `10.81.1.2:1025`. Confirmar que el backend soporta configuración SSR y que no hay migraciones pendientes.
4. El plan Terraform debe mostrar el único bucket nuevo `espacigo-testprod-cloud-build-447373903153`; confirmar ubicación, UBLA, Public Access Prevention, expiración de objetos `source/` a 30 días y `prevent_destroy`. No reutilizar el bucket de archivos ni crear buckets a mano. No hay NAT/router; comprobar que SSR use `PRIVATE_RANGES_ONLY` en `espacigo-testprod-serverless`, mientras SQL/Mailpit siguen en rangos privados por Direct VPC. El watermark `last-successful-main.json` rechaza builds viejos. Si falla un build, el lock permanece y requiere inspección manual antes de retirarlo.
5. Verificar la cuenta y grants mínimos creados desde el plan: `actAs` de la cuenta de build sobre sí misma y las tres cuentas runtime, escritura solo al repo existente, Cloud Run sin permisos delete/Jobs, y ningún acceso a SQL/Secret Manager. Las cuentas runtime mantienen acceso exclusivo a sus secretos.
6. Tras aplicar el plan revisado, en Cloud Build Console conectar exactamente `HernanEspinozaDev/espaciGo`, usar `southamerica-west1`, branch regex `^main$`, seleccionar explícitamente `espacigo-cloud-build-deployer` y apuntar a `cloudbuild.yaml`. Crear el trigger deshabilitado para evitar build automático durante la conexión. El revisor completa configuración inicial de IAP nativo desde Cloud Run Console; no habilita IAP en el balanceador.
7. Lanzar una ejecución manual controlada para un SHA confirmado de `main`; cotejar SHA, digests, provenance y revisión saludable. Las sustituciones de entorno quedan fijadas en YAML. No desplegar migraciones. En cada servicio verificar `status.latestReadyRevisionName`, `status.conditions`, digest de la imagen y `spec.template.vpcAccess.egress=PRIVATE_RANGES_ONLY`. Verificar API privada, web pública por HTTPS en el balanceador existente y web privada con IAP nativo; comprobar `/health/ready`, `/healthz` y el recorrido acordado. El revisor confirma en Console los principales IAP autorizados y pruebas de acceso permitido/denegado.
8. Recién después, habilitar el trigger de `main`, confirmar la exclusión/retirada del publicador y rollout de Actions, y conservar checks de CI.

Cloudflare/DNS mantiene los CNAME actuales al balanceador HTTPS de Santiago, incluidos forwarding rule, proxy HTTPS, certificado administrado, URL map, NEG y Cloud Armor. El web público conserva `internal-and-cloud-load-balancing` y no usa IAP; el servicio privado usa IAP nativo de Cloud Run, no IAP del balanceador. No apuntar DNS a `run.app`, no cambiar la entrada HTTPS ni usar valores de región/CPU/escalado del asistente de Cloud Run. [Cloud Run IAP](https://docs.cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run) documenta IAP de servicio y el acceso por Console; [Cloud Build provenance](https://docs.cloud.google.com/build/docs/securing-builds/generate-validate-build-provenance) requiere declarar `images` y no hacer `docker push` explícito.

## Estado y evidencia

Este PR prepara código, Terraform y controles locales. No ejecuta Cloud Build, Terraform remoto, APIs, conexión GitHub, IAM, Cloud Run, IAP, DNS, SQL ni billing. La cuenta y el bucket no existen hasta aplicar el plan exacto revisado. PR #515 y los previews anteriores permanecen sin cambios y están supersedidos por esta estrategia.
