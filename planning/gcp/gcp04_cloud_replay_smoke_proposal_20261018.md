## Objetivo y alcance

El objetivo de este corte fue comprobar, en recursos run-scoped, el adaptador de replay con PostgreSQL 18 mediante Cloud SQL Go Connector y un bucket GCS real. Se ejecutó un Cloud Run Job privado, de una tarea y una ejecución manual. No desplegó API, scheduler ni workers. Por ello este smoke no demuestra concurrencia entre revisiones de API, liderazgo/fencing de workers, recuperación de backup administrado ni aceptación de producto.

El binario ejecutó la prueba existente `TestGCP04ReplayTwoProcessesPostgres18` y Cloud Run registró `PASS`, `exit(0)` y una tarea exitosa. El padre y dos procesos hijos independientes probaron el replay contra la misma base y bucket. Una barrera SQL obligó a ambos a leer la revisión inicial antes del CAS; las dos escrituras convergieron y el manifiesto final conservó ambas entradas. El bucket real cubrió el CAS de generación y la eliminación exitosa del objeto sintético. El modo local conserva cobertura adicional de respuesta PUT perdida, CAS HTTP 412 y DELETE remoto fallido; esos errores no se inyectaron en Cloud. No se subieron datos de usuarios ni artefactos de ensayos anteriores.

Cada invocación usa prefijos exclusivos `gcp04/<run-id>/privacy` y `gcp04/<run-id>/evidence`. La restauración retrocede una base sintética mediante `CREATE DATABASE ... TEMPLATE` dentro de la instancia desechable; esto no es una restauración de backup de Cloud SQL. El smoke aplica las migraciones runtime V1–V62 en esa base. No modifica archivos SQL ni el historial de migraciones.

### Próximo corte propuesto dentro de GCP-04: GCP-04-W1

Enfocar el siguiente corte de código en el worker durable de borrado de evidencia de privacidad, sin desplegar todavía API ni una flota general de workers. Hoy `cmd/api/main.go` inicia `RunSuppressionCleanupWorkerWithStore` como goroutine cada 10 s. La tabla `baja_archivo_pendiente_local` (V25) guarda disponibilidad/intentos, pero no un claim lease/fencing; `PendingSuppressionFiles` lee pendientes sin `SKIP LOCKED` ni propiedad del claim. `CompleteSuppressionFile` bloquea la fila al finalizar, pero no condiciona la finalización a un token de claim monotónico. Dos procesos pueden seleccionar el mismo trabajo y repetir el efecto externo; el smoke de dos procesos de replay no valida esta coordinación de workers.

Entregable concreto propuesto: separar este único worker del proceso API; añadir un claim atómico con owner/lease y generación de fencing (V63 solo tras revisión del esquema), completar/reintentar únicamente si sigue vigente la generación reclamada, y mantener el borrado GCS idempotente fuera de la transacción SQL. Conservar V1–V62 byte por byte y probar PostgreSQL 18 desde base vacía y actualización desde V62. Criterios de aceptación: dos procesos independientes no poseen el mismo claim vigente; la expiración permite takeover; un proceso viejo no puede finalizar después del takeover; crash tras borrar el objeto y antes del ack converge sin perder la fila; fallo externo mantiene tarea pendiente; las pruebas cubren respuesta repetida y reinicio.
