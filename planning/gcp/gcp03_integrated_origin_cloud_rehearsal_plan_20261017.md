# GCP-03 — plan integrado de ensayo Cloud SQL con snapshot de origen

Fecha: 2026-10-17. Estado: propuesta para revisión técnica; no autoriza infraestructura, transferencia, SQL, jobs ni restore. Base de código: `origin/main` `9a679a3e6bf2c35a43307aeff78ee8f31b7e599d`.

## Objetivo y evidencia de partida

Preparar un ensayo aislado y run-scoped que lleve una copia sellada del origen a una instancia Cloud SQL temporal, la sanee, la verifique y retire únicamente recursos de ese run. La captura local aprobada del 2026-10-17 tiene SHA-256 de `SEALED.json` `80a4e1e0002cf12f8e750ddaac7ceb796726b57a36405aa2b0b8e7852e928262`; su payload cifrado y llave permanecen bajo custodia privada. El restore-copy local corregido concluyó, pero solo comprobó el subconjunto indicado en [la evidencia local](gcp03_local_origin_capture_20261017.md); no acredita compatibilidad con Cloud SQL.

El inventario actual no contiene jobs ni servicios Cloud Run en `southamerica-west1`. Las dos instancias presentes son `espacigo-testprod-pg` y `espacigo-gcp03-pilot01-pg`; ninguna es destino de este plan. La consulta SQL read-only a ambas se bloqueó antes de ejecutar SQL porque `dataApiAccess` no está habilitado. No se habilitará para superar ese bloqueo. El restore synthetic de `gcp03r-1016` y su retirement pertenecen a un contrato distinto: **no reutilizar `cmd/gcp03restore` ni su fase `retire` para el snapshot de origen**. Su restore falló una vez y su ejecución de retire elimina filas específicas de la fixture.

## Diseño por fases y compuertas

Cada fase tiene un plan Terraform independiente, estado remoto con prefijo exclusivo `espacigo/testprod/gcp03-origin/<run-id>`, plan binario privado 0600, JSON saneado y SHA-256 revisado. Un apply/job solo procede tras revisión y liberación específica de esa fase. Terraform nunca invoca jobs. Elegir un `run-id` nuevo e irrepetible; el nombre de bucket queda `espacigo-gcp03-origin-<run-id>` y la instancia `<mismo-prefijo>-pg`.

## Brecha de implementación y cambios requeridos antes del primer plan completo

El root existente `infra/terraform/environments/testprod/gcp03-restore` es exclusivamente la ruta de fixture V1–V61. Sus `enable_diagnostic_job` y verificador diagnostican un target vacío antes de la fixture, pero ese gate está acoplado a `enable_restore_jobs`, que crea a la vez jobs restore/verify/retire e identidades IAM de ese perfil. Su bootstrap y restore usan roles propios del contrato synthetic. No añadir un flag que apunte ese root al snapshot ni activar el retire synthetic.

El siguiente cambio de implementación debe crear un perfil Terraform origen independiente o una extensión que mantenga recursos y estados segregados; gates explícitos `foundation`, `bootstrap`, `observe`, `stage`, `restore`, `verify` y `teardown`; cuenta/verificador sin acceso a artefactos para observación; y executor origen separado que valide estricto el sello/manifiesto y never invoque SQL arbitrario. Compartir solo módulos neutrales de red/Cloud SQL si el plan demuestra que no acopla recursos ni state synthetic. Antes de revisar un apply debe existir plan exacto de foundation y plan de observador sobre el estado creado. Los planes de fases posteriores se refrescan después de cada fase liberada; no es posible construir de antemano un plan binario exacto que incluya recursos/valores aún no existentes.

## Límites, costos y controles de salida

El bloque actual de preflight Cloud SQL documenta dos RUNNABLE existentes, VPC privada y bloqueo de lectura SQL por Data API. La consulta de roles internos, versiones/ACL completas y configuración efectiva debe hacerse después mediante el job aislado, no inferirse desde `gcloud sql users list`. La configuración es explícita a `espacigo-testprod` (proyecto `447373903153`) y `southamerica-west1`; no cambiar billing/quota project ni habilitar APIs, Data API, IP pública, IAM amplio o reglas de red para sortear límites.

Antes de la fase 0, adjuntar cálculo actual de Cloud SQL/Hyperdisk en Santiago para duración propuesta (incluyendo respaldo, disco, logs, red y bucket) y alternativa de duración mensual. Revisé la [tabla oficial de precios de Cloud SQL](https://cloud.google.com/sql/pricing), pero su tabla interactiva no permitió confirmar los SKU regionales exactos en esta revisión; por eso no presento una cifra inferida de una región distinta ni reciclo la estimación histórica de `g03r-1016`. **Costo de fase 0: pendiente; la compuerta no se libera hasta registrar el cálculo oficial y el límite aceptado.** Cada run tendrá límite de tiempo/costo revisado y un responsable de teardown. Cualquier ajuste de costo/capacidad requiere nueva revisión, no una mutación durante la ejecución.

**Fuera de alcance:** nueva captura del origen; descifrado/transferencia; apply o ejecución de job; escrituras en SQL/Cloud Storage; edición de credenciales; activar Data API; cambios a instancias actuales o al repositorio de imágenes; importación a ambiente persistente; apertura de aplicación; aceptación de producto. Ninguno se infiere de una aprobación de este documento o de un PR.
