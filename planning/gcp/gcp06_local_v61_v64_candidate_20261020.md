# GCP-06: preparación local de datos V61 → V64

**Estado:** implementación local candidata para revisión. No autoriza publicación de datos, importación remota ni cambio de tráfico.

## Objetivo de este corte

Preparar un exportador reproducible que lea `espacigo_local` sin escribir en el origen, restaure el snapshot en PostgreSQL 18/PostGIS desechable, sanee las filas copiadas y aplique V62–V64 con el migrador Go de producción. El archivo final queda bajo `.local/testing/` con permisos privados y un manifiesto de conteos y SHA-256.

La implementación está en `scripts/gcp06-local-stage-export.sh` y `scripts/gcp06_stage_sanitize.sql`. El contenedor de staging usa una imagen fijada por digest, red Docker deshabilitada y filesystem temporal. El dump V61 se transmite directamente entre los contenedores; nunca se escribe sin sanear en el host. La herramienta se niega a sobrescribir el directorio de salida y elimina el contenedor al finalizar.

## Política de identidad y publicación

Solo sobreviven las cuentas del namespace sintético `uNNNN@dataset.invalid`. Sus UUID y relaciones de marketplace se conservan; los correos se seudonimizan a `@transfer.invalid`, los teléfonos se limpian y todos los verificadores de contraseña se sustituyen por un valor inválido para autenticación. El estado `activo` se conserva para no cambiar la política de publicación de la cuenta. No se conservan identidades locales, roles de administrador, bootstrap global, sesiones, tokens, verificaciones originales, avisos, outbox, auditoría ni filas que dependan de ellos.

La política privada de cuentas consultada para preparar este corte autoriza solo ensayos locales. No autoriza llevar sus hashes o accesos a Cloud. Para iniciar sesión en un entorno Cloud será necesario un encargo separado y una cuenta creada por el flujo normal de registro/verificación. Este paquete no permite iniciar sesión con las cuentas seudonimizadas.

Como el catálogo requiere elegibilidad KYC, las verificaciones originales se reemplazan en el candidato por marcas fixture sintéticas: proveedor `local-fixture-v1`, referencia `fixture:<UUID>`, revisor sintético sin rol administrador y sin archivos de evidencia ni PII. Se genera una marca solo para propietarios sintéticos con publicaciones activas. No representa KYC real y nunca debe trasladarse a producción ni a un host no allowlisted. El SQL exportado incluye una transacción y un guard que rechaza cualquier base cuyo nombre no cumpla `espacigo_gcp06_candidate_<run-id>`; una futura fase aún debe validar proyecto/instancia allowlisted antes de importar.

## Comando local

Después de revisar este PR y verificar el origen local por el canal autorizado:

```bash
bash scripts/gcp06-local-stage-export.sh .local/testing/gcp06-stage-<run-id>
```

El comando requiere el contenedor local configurado (`espacigo-database-1` por defecto), base `espacigo_local`, PostgreSQL 18 con V1–V61 y la imagen fijada ya disponible localmente. Antes de ejecutar sobre el origen persistente, revisar el script y autorizar una ventana de lectura coherente; el harness de este PR solo usa un origen desechable sintético.

El resultado privado contiene `data.sql` (dump SQL plano PostgreSQL 18 con esquema, seeds estáticos, ledger V1–V64 y datos sanitizados; sin roles, ACL ni ownership; los terminadores COPY `\.` se mantienen) y `manifest.json` (conteos, tamaño, SHA-256, política aplicada y ledger). Los archivos quedan en modo 0600 y el directorio en 0700. No subirlos, adjuntarlos al PR ni copiarlos a un worktree compartido.

## Evidencia local

`scripts/test-gcp06-stage-sanitize-postgres.sh` crea un PostgreSQL 18/PostGIS efímero sin red ni puertos publicados. Comprueba el cierre de taint por claves foráneas, exclusión de cuentas no sintéticas, administradores/sesiones/tokens, pseudonimización y hashes inutilizables; después aplica las migraciones reales V1–V61, ejecuta el exportador completo con datos sintéticos, importa el SQL sanitizado a una base V64 ya migrada en el mismo contenedor aislado; esto no demuestra bootstrap de una base vacía. Una prueba manual con gcloud mock confirmó la precondición de generación cero y la comprobación de generación, tamaño y SHA-256; no contactó Cloud. El bootstrap está bloqueado: V60 exige que `espacigo_gadm_bootstrap` no tenga membresías; PostgreSQL 18 agrega automáticamente al actor con CREATEROLE como miembro del rol que crea. Cloud SQL concede CREATEROLE mediante `cloudsqlsuperuser`. No se modifican V1–V64. No importar el objeto hasta resolver el conflicto mediante un diseño revisado. También confirma que el guard rechaza aplicar el mismo SQL a la base de origen sintética y que esta conserva sus dos filas.

Resultado del harness: prueba del fixture V61, prueba contra el esquema real V1–V61 y prueba end-to-end de exportación sobre un origen sintético finalizaron en `PASS`.

#### Diagnóstico del intento sobre el origen local (2026-10-20)

Un intento del exportador real hacia `.local/testing/gcp06-stage-20261020a` terminó en `local logical snapshot failed`. El contenedor temporal y los archivos parciales se retiraron; el origen no se modificó y no se produjo un dump utilizable. Una ejecución aislada de `pg_dump` terminó con código 0, pero el intento de tubería descartó ambos `stderr`, por lo que no conservó `PIPESTATUS` ni permite atribuir la falla a `pg_dump` o `pg_restore`. El revisor reportó después una ejecución diagnóstica: `pg_dump_exit=0`, `pg_restore_exit=1`, categoría `missing_object`; staging temporal retirado y origen sin cambios. El diagnóstico aún no identifica un objeto específico. No se ha vuelto a ejecutar el exportador contra el origen persistente desde este checkout.

El exportador conserva los `stderr` solo dentro del directorio temporal privado 0700, captura el código de salida de cada extremo y, ante error, emite únicamente códigos y categorías allowlistadas; el contenido crudo se elimina con el contenedor y el temporal. Antes de transmitir filas, compara en read-only el inventario de `pg_catalog` en todos los esquemas no sistémicos (relaciones, constraints, dominios/enums/ranges, rutinas, triggers, collations y extensiones). Los identificadores quedan solo en archivos privados 0600; el reporte expone conteos por clase y hashes, nunca nombres ni valores. El harness sintético comprueba deriva relacional y no relacional, redacción y el recorrido completo.

El inventario GCP-03 versionado registra `fuzzystrmatch`, `postgis_tiger_geocoder` y `postgis_topology` además de las extensiones instaladas por V1–V61 (`btree_gist`, `postgis`, `unaccent`). El staging desechable crea explícitamente las tres extensiones adicionales antes de migrar V1–V61, sin modificar archivos de migración. El harness prueba que el inventario completo de extensiones y objetos de origen sintético queda igual al staging. La revisión reportó que una validación real encontró inicialmente 441 objetos solo en origen, incluidos 3 objetos de extensión, y no generó SQL; la corrección local reduce esa brecha conocida, pero requiere autorización del usuario para una única validación read-only real antes de declarar el staging fiel o producir un artefacto.

La siguiente validación real comunicada por revisión alcanzó inventario idéntico (3.229 objetos) y falló al sanear una fila de `espacio_publicacion_historial_local`: su trigger append-only rechazó el `DELETE` con SQLSTATE `55000`. No se generó SQL; el stage temporal se retiró y el origen permaneció intacto. El saneador vacía los dos ledgers inmutables (`espacio_publicacion_historial_local` y `espacio_eliminacion_historial_local`) solo en el stage temporal mediante `TRUNCATE`, conservando su DDL en el candidato. Un fixture V31 sintético verifica que las filas fuente permanecen en origen, no llegan al candidato y no activan los triggers durante la sanitización. No se repitió el acceso al origen real.

El revisor comunicó después que una ejecución del HEAD anterior falló por FK `ON DELETE RESTRICT` desde `cotizacion_reserva_ensayo` a un usuario marcado para retirar. El staging se limpió, no se produjo SQL y el origen no cambió. El harness se amplió a la cadena V11/V15 completa: cotización, reserva, ocupación circular con ambas FKs `RESTRICT` y usuario tainted. Esa fixture reprodujo el ciclo de borrado: reserva apunta a ocupación y ocupación apunta a reserva. En staging desechable el saneador ahora desvincula temporalmente la ocupación tainted como bloqueo manual, refresca su `ctid`, y después ejecuta el cierre leaf-first. El SQL importado no contiene la cotización, reserva ni ocupación, mientras que el origen sintético conserva las tres filas y el historial append-only. No se repitió la lectura del origen persistente.

La revisión posterior detectó que ese refresco borraba marcadores de todas las ocupaciones tainted, incluidas las manuales. El saneador ahora guarda el CTID original por ocupación de reserva y reemplaza únicamente ese marcador al refrescarlo. El harness añade una ocupación manual ligada a un espacio cuyo dueño está excluido: no se filtra al candidato y permanece en el origen sintético. La exportación, saneamiento e importación completos pasan sin FKs inválidas.

La última revisión observó que un historial append-only de publicación asociado a un propietario tainted puede mantener el espacio por `ON DELETE RESTRICT` y, en consecuencia, bloquear al propietario. El saneador vacía los ledgers en el staging antes del cierre FK; nunca ejecuta `TRUNCATE` contra el origen. El fixture ahora incluye historial de un propietario tainted y valida que ambos registros históricos sintéticos sobreviven intactos en origen mientras candidato queda sin filas de esos ledgers ni espacios/cuentas tainted.

## Fuera de alcance y siguientes gates

`infra/terraform/environments/testprod/gcp06-candidate` define de forma predeterminada apagada un Cloud SQL PostgreSQL 18 privado, la base run-scoped y un bucket privado. Los bindings de importación y carga también están apagados por separado: import usa solo `storage.objects.get`, carga solo `storage.objects.create`, ambos para `gcp06/<run-id>/data.sql` con condición IAM de objeto exacto y expiración UTC máxima de 48 horas. La condición IAM por sí sola no impide nuevas generaciones; la utilidad de subida obliga `--if-generation-match=0` y verifica metadatos. El dump omite rol, ACL y propietario, así que una futura importación necesita un paso revisado que cree los grupos NOLOGIN, revoque y compruebe la membresía ADMIN automática del actor CREATEROLE y configure ACL/ownership de acuerdo con V60/V64 y el contrato runtime aprobado. El bucket elimina el prefijo del run luego de siete días; el cleanup manual de la instancia exige autorización de destroy con el run ID exacto. La raíz no tiene backend remoto.

La validación local con `terraform init -backend=false`, `terraform validate`, `terraform test` (2 casos mock) y plan con refresh apagado confirmó configuración válida, no-op por defecto, destino/proyecto/región fijos, UBLA/PAP, objeto exacto, expiración máxima, create/get mínimos y destroy denegado por defecto. No hizo refresh ni consultó Cloud. No se provisionaron recursos, no se leyó/escribió state remoto, no se subieron artefactos, no se accedió a Cloud SQL, no se cambió IAM/Secret Manager, no se crearon cuentas, no se ejecutaron Jobs, no se modificó el servicio ni el tráfico. La imagen de transferencia G03O publicada previamente es ajena a esta ruta y no se usa en el harness. El harness fijado usa PostgreSQL 18/PostGIS 3.6.4 y una base candidata vacía en el mismo cluster desechable; comprueba que el `CREATE EXTENSION postgis` emitido por `pg_dump` no fija una cláusula `VERSION` y que `psql` instala la versión predeterminada disponible en el servidor de destino. [Cloud SQL documenta PostGIS 3.6.0 como la versión predeterminada en PostgreSQL 18](https://docs.cloud.google.com/sql/docs/postgres/extensions); la prueba local no valida su parser ni ejecuta una importación Cloud SQL. Una ejecución de migraciones con CREATEROLE no-superusuario falla en V60 por la membresía automática; el dump portable evita ejecutar las migraciones en destino, pero no incluye roles/ACL/ownership. Para Cloud SQL quedan pendientes el paso de roles/grants/ownership con membresía ADMIN revocada y comprobada, la allowlist proyecto/instancia, el destino Auth Proxy y la validación real de extensiones; ninguna fase remota forma parte del PR.

### Runbook de roles, ACL y ownership (pendiente de ejecución Cloud)

El dump no lleva roles globales, ACL ni ownership. Antes de conectar una aplicación al candidato, una operación Cloud separada debe: (1) verificar proyecto/instancia/base allowlisted y actor Cloud SQL; (2) crear los grupos NOLOGIN requeridos por V60/V64/runtime usando un actor temporal de CREATEROLE, eliminar ese actor temporal para borrar sus membresías ADMIN implícitas y confirmar que `pg_auth_members` no contiene membresías de `espacigo_gadm_bootstrap`; (3) aplicar ACL exactas del contrato V60, V64 y del bootstrap runtime revisado, y establecer ownership sin transferir extensiones fuera del rol Cloud SQL admitido; (4) comprobar ACL, owners, versiones de extensiones, consulta pública y privilegios del runtime con un ensayo aprobado. El dump importa localmente con propietario `postgres`; ese resultado no fija el owner Cloud esperado. Esta fase no está implementada ni autorizada en este corte. No usar el migrador V1–V64 como usuario CREATEROLE para bootstrap Cloud: V60 detecta la membresía implícita y falla.

Una fase posterior requiere revisar el paquete privado, definir el destino candidato aislado y su costo, revisar Terraform con gates apagados, verificar backup y rollback, decidir ubicación/custodia del artefacto, y autorizar por separado cada operación remota. Archivos privados, clave contractual, preservación del administrador global y aceptación de producto siguen sin resolverse en este corte.
