# GCP-08: restauración gobernada de Cloud Run desde Artifact Registry

**Estado:** implementación de código en revisión. No se creó ni modificó ningún recurso Cloud. El destino que debe usarse es la instancia `espacigo-testprod-db` y la base `espacigo_dms_stage_20261020` (PostgreSQL 18, V67, locale `es_ES.utf8`). Terraform, el verificador y este runbook se fijan a ese destino. El catálogo versionado de `main` aún termina en V66 y no contiene el código asociado a V67, así que ningún baseline V67 ni rollout se puede activar desde este PR.

## Objetivo y límites

Permitir que un operador solicite desde GitHub Actions la restauración de API, web pública y web privada usando exclusivamente digests del manifiesto de una release exitosa de `main`. El flujo no usa Cloud Build, no compila desde source durante restauración, no ejecuta migraciones, SQL, Jobs, seeds, cambios de secretos ni Terraform completo. No selecciona tags mutables ni crea recursos al invocar el asistente Cloud Run.

El workflow manual `gcp08-cloud-run-restore.yml` conserva la restauración inicial `preview`/`apply`: el preview genera un plan binario privado y publica solo un resumen saneado; apply vuelve a planificar, compara resumen/fingerprint y aplica ese plan recién generado. Exige confirmación exacta y gates GCP-08. No se ejecutó ninguna corrida. El flujo de rutina sigue `.github/workflows/application-release.yml` → publicación de digests en `main` → `workflow_run` de `application-rollout.yml`; ese workflow requiere baseline de esquema y `GCP07D_ROLLOUT_ENABLED=true`, y el rollout Terraform solo admite actualizaciones de imagen. El rollout de rutina no sustituye ni evita el preview/apply inicial de GCP-08.

Terraform usa únicamente el root canónico `infra/terraform/environments/testprod/gcp` y el backend `espacigo/testprod/gcp`. La lista `-target` se limita a:

- `google_cloud_run_v2_service.api[0]`, `web["public"]` y `web["private"]`;
- los bindings Cloud Run existentes declarados para invocación pública, IAP, acceso API de los SSR y actualización del deployer;
- los miembros IAP privados configurados en `iap_evaluator_members`, preservando el principal previo y sin publicar su identidad.

Antes del plan, el flujo confirma las direcciones de Cloud Run/IAP en state; el único binding nuevo permitido es acceso de lectura de secreto `roles/secretmanager.secretAccessor` para la cuenta API sobre el secreto V67 exacto. El resumen muestra ese recurso/rol/principal. El verificador exige las tres creaciones de servicio, imágenes por digest, destino SQL V67, usuario `espacigo_api_login` con `SET ROLE espacigo_runtime`, versión numérica de secreto, cuenta runtime, ingress, IAP, rutas `/api/v1`, origen API, allowed hosts y audiencia IAP. Rechaza reemplazos, destrucciones, bindings fuera de la allowlist y cualquier otro cambio. Las lecturas de datos del plan quedan limitadas a la instancia/base y secreto V67 exactos.

## Gates de datos y runtime

El dump restaurado no incluye roles globales; la revisión informó que Cloud SQL actualmente solo lista `postgres`. No se debe asumir que existen `espacigo_runtime`/`espacigo_api_login` ni reutilizar el secreto GCP-06. La ruta de bootstrap propuesta es:

1. Después de fusionar en `main` un PR propio que incluya la migración V67 y el backend/frontend compatibles, exportar evidencia versionada de ese HEAD y establecerlo como baseline solo tras revisión. No copiar la V67 local sin seguimiento ni archivos de otros worktrees.
2. Obtener autorización para una sesión SQL de privilegio mínimo en `espacigo-testprod-db`/`espacigo_dms_stage_20261020`. Antes de DDL, verificar nombre/base, locale `es_ES.utf8`, `server_version_num` PG18 y ledger V67 en modo solo lectura. Ejecutar las migraciones versionadas con el principal migrador aprobado; luego usar el runner soportado del backend para aplicar `dbbootstrap.GrantRuntimePermissions` (misma función que ejecuta `internal/migrator/runner.go`). Registrar el SHA del código y salida saneada.
3. Crear, si no existe, `espacigo_runtime` como `NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT` y `espacigo_api_login` como `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT`; nunca dar `CREATEROLE`, `CREATEDB`, `SUPERUSER`, ownership o membresía ADMIN al login. Aplicar `GRANT CONNECT ON DATABASE espacigo_dms_stage_20261020 TO espacigo_api_login` y `GRANT espacigo_runtime TO espacigo_api_login WITH ADMIN FALSE, INHERIT FALSE, SET TRUE`. Guardar el SQL exacto/aprobación, y luego verificar por consultas de catálogo que el login es LOGIN sin atributos elevados, el runtime es NOLOGIN, la membresía permite SET pero no INHERIT/ADMIN, y los grants de tabla/secuencia/rutina/esquema corresponden a `dbbootstrap.GrantRuntimePermissions`. No registrar hashes ni cargas secretas.
4. Crear el secreto `espacigo-test-database-password-v67` mediante el canal aprobado y cargar como versión su contraseña sin ponerla en argv, shell history, Terraform, logs o artefactos. Solo transferirla por stdin de una sesión segura; eliminar variables temporales al terminar. Consultar únicamente metadatos `gcloud secrets versions describe VERSION --secret=espacigo-test-database-password-v67 --format='value(state)'` y exigir `ENABLED`; nunca ejecutar `versions access`. Anotar solo ID del secreto, número/estado de versión y SHA-256 de la evidencia runtime revisada. Configurar después esos pines como variables GitHub `GCP08_V67_DATABASE_PASSWORD_VERSION` y `GCP08_V67_RUNTIME_PREFLIGHT_SHA`, sin incluir el valor.
5. Revisar el preview GCP-08 que apunta a V67 y muestra el binding de acceso al secreto. Aplicar solo tras revisar el resumen/fingerprint exacto y autorizar el plan; ejecutar smoke checks sin persistir tokens/credenciales.

El workflow no lee el payload del secreto. Exige `confirm_runtime_secret_versions=true`, `confirm_runtime_database_bootstrap=true`, un endpoint Mailpit privado existente y `GCP08_V67_RUNTIME_PREFLIGHT_SHA`, que referencia la evidencia saneada revisada fuera del workflow.

El SHA de evidencia no prueba por sí solo la base; el artefacto revisado debe contener destino, versión de PostgreSQL, locale, ledger/migraciones, extensiones, ownership/ACL, atributos/membresía de roles y estado de versión del secreto, sin contraseñas ni hashes. La revisión de este corte no incluye ese artefacto, por lo que sus gates siguen cerrados.

La release seleccionada debe provenir de `application-release.yml`, ser exitosa en `main`, disponer de su artefacto y contener ambos digests. Se permite un dispatch que solo publicó imágenes (`publish_only=true`), pero se rechaza cualquier release con migraciones. También se verifica que no hayan cambiado después otros archivos de aplicación. Un baseline de esquema `GCP07D_SCHEMA_BASELINE_SHA` válido es obligatorio.

## IAM, WIF, state y acceso privado

El proveedor WIF canónico debe incluir el workflow exacto `gcp08-cloud-run-restore.yml@refs/heads/main` dentro de la condición que ya fija repo/IDs/main/environment. Este PR modifica solo esa allowlist en Terraform; **no aplica** el cambio. La lectura del provider confirmó que hoy permite `application-release.yml` y `application-rollout.yml`, pero no el nuevo workflow; GitHub OIDC no funcionará hasta que el plan IAM de WIF se revise y se aplique por separado.

El deployer observado conserva un rol custom con `run.services.get`, `run.services.update` y `run.operations.get`; no incluye `run.services.create` ni `run.services.setIamPolicy`. El binding de acceso IAP usa además la operación `iap.webServices.setIamPolicy`. Restaurar servicios y bindings requiere esas autorizaciones. No se amplía el rol en este PR: el apply permanece desactivado y debe seguir bloqueado hasta que una revisión IAM separada determine si existe una concesión mínima aprobable para cada permiso, con alcance y revocación exactos. El workflow no crea IAM ni eleva su propia identidad. La ejecución `terraform plan` también necesita acceso de lectura al inventario y al state GCS; el state binario no se publica. Referencias: [permisos IAM de Cloud Run](https://docs.cloud.google.com/run/docs/reference/iam/permissions) y [permisos de políticas IAP por recurso](https://docs.cloud.google.com/iap/docs/managing-access).

El acceso privado se restaura solo con IAP habilitado y los miembros ya declarados en Terraform. Después del apply, una persona/grupo necesita `roles/iap.httpsResourceAccessor` en el recurso Cloud Run privado, además del invoker del agente IAP. La URL privada puede seguir redirigiendo a Google si la identidad no está autorizada.

## Estado observado, preview pendiente y bloqueos vigentes

`main` está en V66 y V67 no está en ningún PR abierto. Por eso el orden obligatorio es: (a) preparar desde un branch limpio basado en `main` el PR V67 de migración/backend/frontend, sin copiar trabajo local no rastreado; (b) revisar/fusionar ese PR y confirmar checks; (c) fijar `GCP07D_SCHEMA_BASELINE_SHA` al commit revisado que contiene V67 y `GCP08_V67_RUNTIME_PREFLIGHT_SHA`/versión solo después de verificar y aprobar el runtime; (d) ejecutar GCP-08 `preview`, revisar fingerprint y destino V67, y autorizar un único `apply`; (e) solo tras su éxito, habilitar `GCP07D_ROLLOUT_ENABLED=true` para los siguientes merges aprobados a `main`. GCP-07D ya verifica que cada manifiesto de publicación desciende del baseline y que no contiene migraciones, y su plan allowlistado solo cambia imágenes. No fijar baseline V66 ni publicar/deplegar una release incompatible con la V67 cargada.

Al habilitar rutina, `application-rollout.yml` fija en los tfvars efímeros `espacigo-testprod-db`/`espacigo_dms_stage_20261020` y la versión numérica aprobada; exige referencia de preflight, bootstrap confirmado y las variables anteriores antes de OIDC. Cada release exitosa de imágenes en `main` dispara ese rollout por `workflow_run`. Reversa: aplicar mediante el camino GCP-07D con preview/fingerprint el digest previo de cada componente, solo si el plan sigue limitado a imágenes; esto no revierte migraciones ni datos. Si falla API con V67, detener futuros rollouts y volver a los digests anteriores; no apuntar a la candidata GCP-06 ni ejecutar DDL inverso.

El state tras el borrado manual se comprobó mediante `terraform state list` filtrado; permanecen las tres direcciones Cloud Run y ocho bindings: dos `api_invoker`, tres `deployer_service_updater`, `public_web_invoker`, `private_iap_invoker` y un principal IAP privado. No se publicó la identidad privada IAP. Si el plan detecta que un binding existente es diferente del valor configurado, el allowlist lo rechazará; el flujo no importa recursos ni modifica el state manualmente.
