## Alcance del ejecutor

`cmd/gcp03scratch` acepta fases fijas para `bootstrap`, `database_acl`, `migrate`, `finalize`, `grant_owner_history`, `retire`, `verify_retired`, `revoke_retired_membership`, `observe` y las sondas de membresía. El binario fija proyecto, región, instancia, base, login por fase, URL sin password, ruta del secreto y modo de IP privada. Rechaza overrides de libpq/pgx, SQL de entorno, URLs distintas y contraseñas fuera del formato aleatorio. Usa el adaptador Cloud SQL compartido y las migraciones V1–V61; no expone SQL arbitrario.

| Fase | Acción fija | Condición de salida |
| --- | --- | --- |
| `bootstrap` | Instala extensiones y precrea los dos roles de grupo fijos sin login; comprueba el estado de PostgreSQL 18. | Puede quedar la membresía ADMIN que PostgreSQL concede al creador CREATEROLE. |
| `database_acl` | Con la credencial temporal de `postgres`, quita TEMP de PUBLIC y CREATE de PUBLIC en `public`, concede TEMP de base y CREATE de schema al migrador y valida ACL positivas/negativas. | Solo el migrador conserva TEMP/schema CREATE antes de las migraciones. |
| `migrate` | Comprueba roles reconciliados y ACL de base/schema, y llama al runner para V1–V61 sin cambios. | Secuencia y checksum por versión verificados. |
| `finalize` | Exige historial completo V1–V61; aplica `GrantRuntimePermissions`; comprueba atributos V60, roles y permisos positivos/negativos. | Contrato de permisos runtime verificado. |
| `retire` | Con el owner temporal, verifica historial y grants, deshabilita login/atributos del migrador y revoca su TEMP y CREATE en schema. | Solicita una verificación independiente antes de limpiar la membresía Cloud SQL o rotar credenciales. |
| `verify_retired` | Con el owner temporal, en transacción `READ ONLY`, observa roles/membresías, ACL y propietarios, privilegios efectivos, checks runtime e historial V1–V61. | El reporte completo queda disponible para revisión aunque alguno de los checks falle. |
| `revoke_retired_membership` | Con el owner temporal, valida V1–V61, ACL de historial, atributos y la única membresía `cloudsqlsuperuser` esperada del migrador; emite solo el `REVOKE` fijo dentro de una transacción. | Confirma cero membresías y el contrato retirado completo; confirma solo si todos los checks pasan. De lo contrario revierte y emite diagnósticos sanitizados. |

No se borra el rol migrador: puede ser propietario de objetos de migración. PostgreSQL 18 concede al creador ADMIN sobre los NOLOGIN roles recién creados, y el creador no puede quitar su propio autogrant. Entre `bootstrap` y `database_acl`, el operador usa `gcp03scratch-credential --apply --reconcile-creator-memberships --confirm-target=RECONCILE:<target>`; Cloud SQL Admin `users.update` debe conservar solo `cloudsqlsuperuser` y reemplazar las demás membresías. La fase `database_acl` usa una segunda cuenta runtime, con Cloud SQL Client y acceso solo a metadata/versión del secreto owner. Al terminar `retire`, el operador revoca todas las databaseRoles del migrador y destruye su versión exacta. Luego rota `postgres` a una contraseña aleatoria no guardada y destruye la versión exacta usada por ambas fases owner. Las llamadas y el comportamiento de Cloud SQL Admin deben verificarse en el entorno destino antes de una futura ejecución; esta revisión no usa el API.

`verify_retired` es una fase independiente, protegida y de solo lectura para ejecutarse con la cuenta owner después de retirar el login temporal. Abre una transacción `READ ONLY`, recopila el inventario fijo de roles, membresías, ACL y propietarios; registra los privilegios TEMP/CREATE efectivos, verifica las 61 sumas de migración y todos los checks runtime, e informa el resultado aunque fallen las comprobaciones de retiro. No rota credenciales ni modifica roles o ACL. Su Job usa una compuerta Terraform e imagen por digest separadas.

`revoke_retired_membership` es una fase separada con compuerta Terraform apagada por defecto. Su única mutación prevista es `REVOKE cloudsqlsuperuser FROM espacigo_scratch_migrator`; no cambia atributos ni ownership. La prueba local PostgreSQL 18 demuestra únicamente la mecánica del grantor con ADMIN OPTION y el rollback sin ADMIN, no la capacidad equivalente de Cloud SQL. La fase no se ejecuta en Cloud SQL hasta que código, OCI y plan exacto hayan sido revisados.

## Creación inicial de la credencial temporal

Terraform continúa administrando solo metadata del secreto. Un operador autenticado ejecuta localmente `gcp03scratch-credential --apply --confirm-target=CREATE:<target>`. El CLI genera 32 bytes aleatorios, los representa como Base64 URL sin padding, agrega una versión al recurso fijo `projects/espacigo-testprod/secrets/espacigo-gcp03-pilot01-migrator-password`, crea el login integrado exacto por Cloud SQL Admin API y espera la operación. No imprime ni recibe una contraseña en argumentos; los resultados inciertos conservan la versión para conciliación.

Cloud SQL asigna inicialmente `cloudsqlsuperuser` a un usuario PostgreSQL integrado cuando no se especifican roles personalizados. La retirada documentada por Google usa `users.update` con `databaseRoles: []` y `revokeExistingRoles: true`; aquí solo ocurre después de la fase SQL que ya dejó el login `NOLOGIN`. Referencias: [crear y administrar usuarios PostgreSQL](https://docs.cloud.google.com/sql/docs/postgres/create-manage-users) y [método REST users.update](https://cloud.google.com/sql/docs/postgres/admin-api/rest/v1beta4/users/update).

## Jobs e IAM

El root aislado define cinco Jobs Cloud Run independientes (`bootstrap`, `database_acl`, `migrate`, `finalize`, `retire`), cada uno con una tarea, paralelismo 1, cero reintentos, cuatro horas, 2 vCPU/4 GiB y digest inmutable. El gate permanece apagado por defecto y Terraform exige el scratch exacto, digest de la imagen, y versiones Secret Manager numéricas exactas (nunca `latest`) para migrador y owner.

- Identidad de migraciones: `roles/cloudsql.client` y `roles/secretmanager.secretAccessor` solo para el secreto migrador. No recibe Cloud SQL Admin, secretos de aplicación, bucket de archivos, ni `Editor`/`Owner`.
- Identidad owner: `roles/cloudsql.client` y `roles/secretmanager.secretAccessor` para el secreto owner temporal. Solo ejecuta las fases fijas de ACL/retiro; no recibe Cloud SQL Admin.
- Service agent de Cloud Run: `roles/artifactregistry.reader` limitado al repositorio scratch.
- Operador de Jobs: `roles/run.invoker` en cada Job y `roles/iam.serviceAccountUser` solo sobre la cuenta runtime scratch.
- CLI de credenciales: el plan vigente define roles custom temporales con IDs nuevos, `cloudsql.instances.get` y `cloudsql.users.create/get/update` sin `users.delete`, y `secretmanager.versions.add/destroy/get/list` atado mediante dos bindings a los secretos migrador y owner exactos; excluye `versions.access`. El binding Cloud SQL es de proyecto y de corta expiración; la limitación está en [permisos IAM para Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/iam-permissions). Ningún rol se concede a las service accounts runtime. El plan y hashes están en [plan IAM temporal de replay](gcp03_replay_credential_iam_plan_20261016.md). Las propuestas anteriores de `secretVersionManager` y el rol del probe no son el plan vigente del replay. No otorgar roles predefinidos amplios como Cloud SQL Admin o Secret Manager Admin.

## IAM temporal de operador de credenciales

La creación/revocación de usuario y versiones no se hace desde Terraform ni desde el Job. El plan local vigente contiene un binding Cloud SQL temporal a nivel proyecto y dos bindings de versiones limitados a cada secreto scratch. Su TTL absoluto debe revisarse en el momento de apply. No se aplicó. Después de la liberación del plan, el CLI crea credenciales y devuelve versiones numéricas; solamente entonces se prepara el plan de Jobs fijado a esos números. Retirar los permisos temporales después de crear/conciliar las credenciales y al final de revocar los roles y destruir las versiones. El service account runtime permanece sin esos permisos.
