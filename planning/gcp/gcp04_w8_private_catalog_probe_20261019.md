# GCP-04-W8 — primera sonda privada de catálogos

**Estado:** implementación local y manifest de liberación propuesto; rol candidato y compatibilidad con Cloud SQL Admin API sin resolver. No hay autorización ni ejecución de mutaciones Cloud.

## Objetivo y separación de W7

W8 agrega una sonda inicial separada de `cmd/gcp04preflight` y de su login W7. `cmd/gcp04w8catalogprobe` fija proyecto, instancia, IP, base, login candidato, archivo SQL, digest, secreto numérico y timeout. Comprueba la IP observada del socket del Cloud SQL Connector antes de la transacción; comienza una transacción PostgreSQL `READ ONLY`; verifica base, login, PostgreSQL 18 y `transaction_read_only`; y emite únicamente JSON de una consulta allowlisted. No acepta un SQL arbitrario. La imagen Docker local copia solo esta consulta y no incorpora un cliente de mutación de Cloud SQL Admin API.

La consulta enumera roles seleccionados (`espacigo_db_observer`, `pg_read_all_settings`, y el nuevo login candidato), el cierre recursivo de membresías heredadas/accesibles desde el login, las aristas relacionadas y ACL de la base actual, schema `public` y ledger `public.schema_migrations` cuando existe. No lee filas de negocio, vistas de configuración o estadísticas, catálogos de autenticación sensibles, comentarios, contraseñas o payloads de secretos. El binario extrae y ejecuta únicamente el `SELECT` entre `BEGIN READ ONLY` y `COMMIT` del archivo fijado por SHA-256 `3fc825934660bbfc965e8d97b2ef7f4648baf2cded6c8871ae6953bd18c70d16`; pgx administra la transacción y recibe una sola sentencia preparada.

## Decisión pendiente sobre identidad

Cloud SQL documenta que una cuenta builtin creada sin roles personalizados recibe `cloudsqlsuperuser`; por ello la propuesta nunca omite `databaseRoles`. El Admin API modela `databaseRoles[]` como strings y la guía indica que un rol personalizado debe existir antes de asignarlo. La documentación no confirma de forma explícita que `users.insert` acepte `pg_read_all_settings` (rol predefinido de PostgreSQL) para la creación de este usuario builtin. El request de dry-run muestra el valor explícito `databaseRoles=["pg_read_all_settings"]`, pero no se envía a Cloud.

PostgreSQL documenta que `pg_read_all_settings` permite leer todas las variables de configuración, incluidas las normalmente visibles solo para superusuarios. Esa amplitud deja un riesgo residual aun cuando la consulta W8 no lea vistas de configuración. Por tanto el rol no está aprobado: antes de una operación de creación, revisión debe decidir si la amplitud es aceptable o pedir un rol más estrecho y confirmar compatibilidad del API. No se usará `pg_monitor`, `pg_read_all_stats`, `pg_read_all_data`, `cloudsqlsuperuser` ni una lista vacía.

## Helper y manifest

`internal/gcp04w8release` solo contiene lectores de metadata y un builder `dry_run_only`; no tiene método mutador. El secreto candidato usa el recurso del API global `projects/espacigo-testprod/secrets/espacigo-gcp04-w8-catalog-probe-password`, con replicación `USER_MANAGED` y una sola réplica inmutable en `southamerica-west1`. Cloud Run Jobs no admite el recurso del API regional de Secret Manager; el Job usará el ID de secreto del mismo proyecto (no el resource name regional) y montará su versión numérica como archivo. El secreto global con réplica gestionada por el usuario conserva el límite de residencia. El helper relee metadata exacta de instancia, inventario de usuarios, metadata del secreto global y versiones. Aborta por drift, política/región distinta, inventario incompleto o colisión del login/versiones. No genera password, no crea versión ni usuario y no llama a un mutador. El request propuesto contiene tipo `BUILT_IN` y un array `databaseRoles` exacto y no vacío.

El manifest JSON registra target/connection/IP, request propuesto, digest SQL, recurso global y réplica regional única, digest de imagen aún pendiente, identidad del Job/SA, IAM acotado, secuencia de creación propuesta, abortos/reconciliación y teardown solo de recursos exactos W8. La contraseña se describe como memoria efímera y el secreto como versión numérica del recurso global, replicada en `southamerica-west1`; el payload no aparece en Terraform, argumentos, logs o salida. No hay recurso Terraform para una versión secreta, porque el proveedor guarda `secret_data` en state sin procesar. La publicación del digest, generación/adición de secreto, `CREATE_USER`, IAM, Job y ejecución requieren un corte y autorización posteriores.

Secuencia de propuesta: (1) exigir, desde una liberación revisada separada, el recurso global sin payload con replicación `USER_MANAGED` a una sola región `southamerica-west1`; (2) releer metadata/usuarios/versiones; (3) abortar ante colisión sin reset ni update; (4) revisar el rol y soporte Admin API; (5) generar password en proceso; (6) agregar una versión por el API global y conservar solo su número; (7) crear exclusivamente el usuario nuevo con roles explícitos; (8) preparar IAM y Job aislado con digest aprobado; (9) ejecutar la consulta una vez bajo autorización aparte. Un resultado incierto se reconcilia por recursos exactos y no se repite a ciegas.
