## 5. Cambios de aplicación necesarios antes de desplegar

1. **Persistencia de archivos:** GCP-01 incorpora el adaptador Cloud Storage para blobs con UUID y precondición create-only, manteniendo metadata en PostgreSQL y autorización pública/privada de Go. El adaptador de blobs no resuelve `LOCAL_PRIVACY_REPLAY_FILE`: el registro replay todavía usa reemplazo atómico local (`CreateTemp`/`Rename`). Hasta moverlo a un puerto con persistencia compartida y probar idempotencia, concurrencia y recuperación, el perfil de ensayo no está listo para Cloud Run. Antes del despliegue probar archivo ausente, timeout, escritura confirmada sin respuesta, limpieza y lectura entre dos instancias reales; los tests locales usan un endpoint HTTP falso.
2. **Imagen Go:** GCP-01 copia el bundle CA raíz desde la etapa Alpine al runtime `scratch`; el usuario sin privilegios y tzdata embebida se conservan. Se validó la compilación local de esa imagen, no una conexión HTTPS real a Google APIs ni Cloud SQL.
3. **Configuración Cloud SQL:** el perfil local incorpora `DATABASE_CONNECTION_MODE=cloudsql`, Cloud SQL Go Connector con ADC y selección de IP privada, contraseña runtime desde archivo protegido y pool por instancia. El conector aplica TLS autenticado, pero no crea VPC, rutas o acceso privado. IAM DB auth no está implementada en esta iteración; el despliegue previsto montará una contraseña de runtime desde Secret Manager con acceso mínimo. La configuración de código tiene pool predeterminado 10 y máximo 50; no es una recomendación para multiplicar 50 por cada revisión. Candidato inicial de ensayo para Terraform: API con `DATABASE_POOL_MAX_CONNS=10`, máximo 1 instancia por revisión y máximo 2 revisiones atendiendo durante rollout: hasta 20 conexiones API; más 1 migrador y 5 reservadas para administración/operación, total previsto 26. Es solo un techo de diseño, condicionado a leer `max_connections` y concurrencia efectiva de Cloud SQL antes de fijarlo en código Terraform. Fórmula de aceptación: `instancias_por_revision × pool_por_instancia × revisiones_simultáneas + migrador + reserva_operativa <= max_connections` observado. Los workers actuales comparten el pool del API, pero la coordinación entre revisiones sigue pendiente; GCP-04 debe confirmar esa premisa con lease y pruebas.
4. **Workers:** el perfil actual sigue iniciando reconciliadores, limpieza y outbox junto con cada proceso API. No hay lease de liderazgo entre procesos ni revisiones; dos revisiones vivas pueden ejecutar workers duplicados. Para despliegue, GCP-04 debe separar o coordinar workers mediante lease PostgreSQL probado con terminación/reinicio, o mantener una única instancia/proceso sin solapamiento comprobado y demostrar que el rollout no duplica la ejecución. No desactivar sweeps para ocultar trabajo pendiente. GCP-01 no certifica idempotencia de esos workers en Cloud Run.
5. **Angular/gateway:** Cloud Run requiere API interno HTTPS y audiencia igual a su origen de servicio; el token de invocación se obtiene en el servidor y se envía en `X-Serverless-Authorization`, mientras `Authorization: Bearer` conserva el token del usuario para Go. El gateway nunca reenvía `X-Serverless-Authorization`, IAP assertion, cookies o credenciales IAM aportadas por el cliente; no publica el token IAM al navegador. La audiencia no incluye un path y debe coincidir con la URL `run.app` del API, aunque la llamada agregue `/api/v1`. En Cloud Run el `API_PUBLIC_BASE_URL` es exclusivamente `/api/v1` same-origin. La política pública comprobable permite GET anónimos sin cuerpo de catálogo/detalle/categorías/ubicaciones, rechaza métodos privados, credenciales y rutas codificadas, limita URL a 4 KiB, espera hasta 10 s por respuesta y limita JSON público a 2 MiB e imagen a 1 MiB. El sitemap permite hasta 2.000 páginas de 25 resultados y 49.996 IDs. Solo respuestas de rutas públicas con `Cache-Control: public, max-age` explícito de hasta 300 s son cacheables; todo lo demás es `private, no-store`. Aún no hay cuota agregada por IP en el proceso Angular: antes de admitir tráfico público, GCP-02 debe configurar Cloud Armor en el balanceador con 60 solicitudes/minuto por IP al catálogo y 120/minuto al origen público, y demostrar que superar cada cuota devuelve 429 y que se recupera al vencer la ventana. Estos límites son criterios iniciales del ensayo, sujetos al inventario de tráfico y costo; el límite de bytes/tiempo local no los sustituye. La llave de rate limit debe ser una IP de origen validada por el balanceador: si Cloudflare usa proxy, no confiar en `X-Forwarded-For`/`CF-Connecting-IP` no autenticado; preferir DNS-only o verificar un canal de origen que impida falsificarlos. El servicio Cloud Run privado/API no tendrá `allUsers` ni acceso directo alternativo que evite IAP/IAM. **IAP se habilita directamente en el servicio Cloud Run privado**, no en el backend del balanceador. Su audiencia tiene forma `/projects/PROJECT_NUMBER/locations/REGION/services/SERVICE_NAME`; el servicio usa `INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER` y solo IAP/evaluadores explícitos lo invocan. La entrada privada valida criptográficamente `x-goog-iap-jwt-assertion` con las claves públicas oficiales de IAP: `alg=ES256`, `kid`, firma, emisor, audiencia exacta y `iat`/`exp` con 30 s de tolerancia; falla cerrada si falta `IAP_JWT_AUDIENCE` o la verificación no está disponible, salvo `/healthz` y `/health/ready`. `API_SERVICE_AUDIENCE` es el origen HTTPS del API para el ID token de invocación. SSR solo añade ese ID token al origen/ruta `/api/v1` configurados y excluye esas solicitudes del TransferCache, sin serializar la credencial al navegador. La entrada pública expone el origen privado en `/config.json`; guards ejecutados por navegación SPA usan navegación de documento y conservan solo retornos aceptados por `parseIdentityReturn`. GCP-02 debe verificar IAP nativo de Cloud Run, el cierre de invocación directa `run.app` y el OAuth de la topología real; las pruebas locales no acreditan infraestructura ni claves de producción. No trasladar `127.0.0.1` al navegador; preservar rutas, guards y Go como autoridad.
**Preflight de claves IAP:** la verificación Express actual obtiene `https://www.gstatic.com/iap/verify/public_key`. La documentación de Google lista `gstatic.com`/`*.gstatic.com` entre los dominios de servicios compatibles con Private Google Access; Cloud Run permite que el tráfico `ALL_TRAFFIC` por Direct VPC use PGA en la subred y el route por defecto al internet gateway para alcanzar servicios Google elegibles. Por ello no se propone NAT para este destino concreto, que sigue dentro de la red de Google; destinos públicos no Google quedan fuera. La topología no cuenta con prueba real aún: la variable `confirm_pga_iap_key_preflight` queda falsa y bloquea `enable_services` hasta verificar el GET desde una ruta Cloud Run equivalente. Si falla, mantener el servicio apagado y someter alternativa/NAT a revisión de alcance y costo. Fuentes: https://docs.cloud.google.com/vpc/docs/private-access-options, https://docs.cloud.google.com/vpc/docs/configure-private-google-access y https://docs.cloud.google.com/run/docs/securing/private-networking.

**Orden y gates de arranque GCP-02:** todas las identidades, IAM, Artifact Registry, Storage, Secret Manager, SQL, Cloud Run y balanceador esperan que finalice la habilitación de la API requerida. El API espera sus grants Cloud Storage, Secret Manager y Cloud SQL; los SSR esperan `roles/run.invoker` sobre el API; Terraform genera la identidad administrada de IAP antes de otorgarle `roles/run.invoker`, y el forwarding rule queda tras los bindings de las entradas pública e IAP. Las versiones de Secret Manager no se cargan en Terraform: `confirm_runtime_secret_versions` queda false hasta cargarlas por canal privado. El usuario y grants PostgreSQL tampoco se almacenan en state: `confirm_runtime_database_bootstrap` queda false hasta crear y probar el rol least-privilege. Junto al preflight PGA/IAP-key, replay/leases GCP-04 y Mailpit privado, esos gates impiden crear servicios prematuramente.

6. **Perfil cloud de ensayo:** mantener proveedores fake explícitos sin introducir bypass de autorización, exponer fixtures administrativos o convertirlos en proveedores reales. El reloj normal de la API pública sigue real. Para el piloto autorizado de tratos se permite un reloj manual solo en un proceso/API aislado de ensayo, con identidad y endpoint no públicos, asociado a la base persistente únicamente durante el piloto y la carga autorizada. Al finalizar: detener el proceso aislado, restablecer/verificar reloj normal y auditar conteos/hashes; ninguna instancia pública puede ver el reloj manual ni procesar reservas concurrentemente durante la ventana. Ejecutar los 10 casos piloto y validar resultados antes de la carga persistente de 1.200.

### Correo de ensayo compatible con Cloud Run

La implementación Go usa SMTP convencional (`LOCAL_SMTP_ADDR`) y outbox durable en PostgreSQL. No se alojará Mailpit como servicio Cloud Run esperando tráfico entrante SMTP: la entrada Cloud Run está diseñada para HTTP/gRPC y no expone un puerto SMTP independiente. La opción elegida para el ensayo es una VM pequeña y dedicada en la VPC, con Mailpit, almacenamiento de mensajes en un disco persistente, SMTP privado en el puerto 1025 y UI/API solo por túnel IAP para evaluadores. La API Cloud Run llegará al SMTP por Direct VPC egress; una regla de firewall limitará 1025 a la identidad/red de la API. No tendrá IP pública ni SMTP relay externo. `LOCAL_SMTP_ADDR` apuntará a su IP privada. El outbox de PostgreSQL conserva/reintenta la intención durable si Mailpit no está disponible; el volumen de Mailpit preserva los mensajes aceptados y se respaldará según el plan de ensayo. El acceso a bandeja y búsqueda queda limitado a evaluadores, nunca a la entrada pública.

Esta topología requiere VM/disco/firewall/VPC en Terraform y está fuera de GCP-01: no crearla ni modificar recursos para probarla localmente. En local se sigue usando Mailpit dedicado de Compose. Antes de GCP-05 se debe probar apagado/reinicio de la VM, persistencia del buzón, restauración de la outbox tras SMTP indisponible, reintento, verificación de destinatarios `*.invalid` y ausencia de relay hacia correos reales.
